# Agent Note: 环境感知的 HTML→PDF 渲染与优雅降级

Status: proposed

[English](2026-09-01-env-aware-rendering-graceful-fallback.md) | 中文

## 问题

在会话 `dsh-session-463b73d4`（报告生成任务）中，智能体基于 Chrome DevTools Protocol（CDP）搭建 HTML→PDF 管线，并在 `workspace-write` 沙箱下运行；该沙箱中 Chrome 的调试端口和 DevTools websocket 无法启动。它在这条注定失败的路上重试了约六次：一次 51s 的 CDP 就绪探测、两次分别等满 138s 和 144s 的 `job_output`（都以 `RuntimeError: Chrome 调试端口未就绪` 结束），以及三次精确到 60s 超时被杀的 `bash`。这一簇（step 56–90）在智能体转向其他方案前消耗了本次 72 分钟会话约 20 分钟。

`pandoc`、`wkhtmltopdf` 和 `soffice` 都存在，且在 step 6 已被探测到，但智能体仍一路走向 CDP。harness 没有给出「所选引擎在当前沙箱不可用」的信号，也没有提供切到可用引擎的更省时路径。

## 提案

新增一个环境感知的渲染能力，供报告/交付工具链用于 HTML→PDF。渲染前执行一次廉价、有界、服从取消信号的探测，判断候选引擎能否在当前沙箱里运行（对 Chrome 而言，即 `--headless --remote-debugging-port` 能起来且 DevTools 端点有响应）。失败时按文档化顺序——`pandoc`、`wkhtmltopdf`、`weasyprint`、LibreOffice `soffice`，最后是明确报错——推进到首个探测通过的引擎。探测结论在会话内缓存，渲染不重复支付该代价，且会话内不再重试已被确认不可用的引擎。

该能力记录实际产生输出的引擎以及采用的降级链，使构建可复现、可诊断。当所有引擎都不可用时，一次渲染在渲染步骤就明确失败，而不是循环重试。

## 考虑过的替代方案

- **继续重试 CDP。** 保留了单一引擎，但在沙箱禁止的路径上烧掉墙钟时间。
- **硬编码单一引擎。** 只在引擎存在且被允许的环境里有效；在其他沙箱里会失败。
- **让每个调用方各自探测。** 逻辑重复，可用性排序各异。
- **每次渲染都探测。** 正确，但重付了会话缓存本该吸收的探测成本。

## 接受标准

- 在 Chrome 调试端口不可用的沙箱里，一次渲染请求能在有界的引擎尝试次数内通过降级引擎完成；已被确认不可用的引擎在该会话内不再重试。
- 在 Chrome 可用的沙箱里，使用首选引擎。
- 渲染结果记录引擎和降级链。
- 探测本身有界、服从取消信号，绝不会让渲染挂死。
- 测试覆盖探测缓存、降级顺序、所有引擎不可用时的明确报错，以及选择结果与文档化可用性一致。

## 风险

降级引擎的版式和分页不同；该能力必须定义调用方如何接受降级输出，或改用文本校验而不是依赖像素级一致的渲染。在没有任何渲染引擎的沙箱里，探测顺序和可用性检测本身也不准成为新的慢路径。
