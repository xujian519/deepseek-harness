# Agent Note：PatentTeams 团队页签仪表盘与历史排水

Status: implemented

[English](2026-09-03-patent-teams-dashboard-and-history-drain.md) | 中文

## 问题

两个缺口落在同一个面上。其一，固定的"团队"tab 把折叠出的团队渲染成朴素行列表：没有一眼可见的进度、任务之间没有依赖关系、成员没有任务绑定、也没有近期动态——与该功能改造来源的上游 `@nanmicoder/dsh-agent-teams` 活动面板相比视觉差距明显。其二，一次现场报告显示团队明明在工作、页签却卡在空态：长会话打开时只加载尾部历史窗口（最近 50 条消息），折叠需要每个团队唯一的 `team-created` start 事件，而"团队"tab 上没有任何东西会向前翻页——窗口里的全部 update 事件因此保持搁置，快照一直是空的。

## 决策

- "团队"视图按团队渲染一个仪表盘区块（`TeamsDashboard.tsx`）：Hero 区含完成环、分段进度条（`taskSegments` 得出的已完成/执行中/等待）、带队长通栏卡的花名册（按成员 id 派生渐变头像）以及带当前/上一任务绑定的实时成员状态；任务依赖图按依赖深度分层、曲线连接（`teams-dag.ts`，循环安全的最长路径分层），悬停追踪、点击固定依赖链；外加封顶的最近动态流。聊天卡片的渲染不变——tab 与卡片仍是同一折叠的投影。
- 折叠保留每团队封顶的动态流：`applyTeamsEvent` 记录最近八条任务迁移与邮箱消息（`TEAMS_ACTIVITY_LIMIT`），以 `PatentTeamsCardData.activity` 按 newest-first 投影。这是投影上的增量字段；聊天卡片忽略它。
- 假空态在视图层修复而非数据层：折叠中没有任何团队且窗口还有更多历史时，`TeamsView` 持续调用注入的 `loadOlder`（Session 面的向前翻页动词，在 slot 的 `inject` 中解析，与轨迹视图的做法完全一致），上限 400 页，卸载后的迟到完成被丢弃。start 事件一进窗口，排水即停。
- 上游的交互词汇（分段进度、花名册、依赖图）被有意采纳；其 body-portal 浮层与轮询 host 路由仍被拒绝——tab 依旧只渲染会话日志重放产出的内容。

## 曾考虑的替代方案

**host 侧投影（读会话投影而非客户端折叠）。** 暂不采纳：投影面会复制聊天卡片与 tab 必须共享的折叠 reducer，而排水以极小的改动修掉了真实故障。

**无 start 团队的降级渲染（仅凭 update 建节点）。** 拒绝：成员与任务列表会部分且误导性地渲染；空态加自动排水既诚实又能自愈。

**每个视图在会话打开时自动加载全量历史。** 拒绝：为了让一个 tab 受益而向每次会话打开征税；排水只在"团队"tab 的折叠为空且还有更多历史时运行。

## 后果

- 长会话中的团队进度无需手动滚动即可实时呈现；该修复用户可见，与仪表盘属于同一 PR。
- `PatentTeamsCardData` 新增必填 `activity` 字段（仅一处构造）；该投影类型的外部生产者需在下一次构建时补齐。
- DAG 布局由折叠顺序决定、纯且确定；团队状态里的依赖环不会挂死布局（回边按根深度解析）。
- 在真实现场会话上做实机验证时发现一个更深的、排水无法覆盖的服务端案例：harness 重启后继续（continued）的会话，其服务日志是重新播种的（游标停在种子边界、`hasMore` 为 false），种子只携带模型可见事件——ignorable 的 `patent-teams/*` 事件不再进入日志，折叠无论如何加载历史都无法重建团队。要关闭该案例需要种子/持久化层的决策：让 ignorable 插件事件随种子保留，或给视图一个读取磁盘团队状态真值的 host 面（即上游项目的磁盘真值路线）。

## 测试

`vitest run packages/client/ui-patent-teams` 全绿（49 例），包内逐文件 100% 覆盖：`teams-dag.spec.ts` 钉住布局确定性、循环容忍、链闭包、分段计数与任务绑定；fold spec 钉住封顶 newest-first 动态流与未知任务裁决；客户端 spec 钉住仪表盘渲染（Hero、图例、花名册绑定、DAG hot/dim 状态、动态种类）、排水循环、停止条件与卸载竞态；插件生命周期用例演练视图入口的 label、inject 与缺失绑定的响亮抛错。
