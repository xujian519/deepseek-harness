# Agent Note: 案卷日志的取代链作为交付前置条件

Status: implemented

[English](2026-10-12-matter-log-supersede-chain-gate.md) | 中文

## Problem

案卷审计链（`_matter-log.md`）此前只靠约定维持只追加：模型用通用文件工具写它，因此字段集、只追加规则与取代链全部依赖自觉遵守。版本号只是文件头里的一句自述，于是没有任何东西记录哪一份交付件取代了哪一份、为什么取代；也没有东西阻止某一轮把上一轮的文件覆盖掉，或整轮不留任何记录。那一轮改了什么、为什么改、是否影响保护点，事后都无从从案卷中复原。

2026-09-30 对标清单（`2026-09-30-patent-domain-external-benchmark.md` 的 P0-1 项）把这两处缺口并作一条，要求给出执行点而不是更严格的约定，并按本仓的要求做改造：日志为源、文件为投影，不照抄来源项目的「时间戳文件名即版本历史」。

## Decision

- `@deepseek-ai/dsh-patent-tools` 注册第 33 个模型工具 `matter_log_append`，作为案卷 `_matter-log.md` 的唯一写入口。一次调用追加一条条目——本地时间 + UTC、动作、产物、本轮取代的路径、审批人、本轮变更说明——不改动其他任何内容；文件中既有字节作为前缀原样保留。
- 自由文本字段承载本轮留档内容：改了什么、为什么、是否影响保护点。这正是借鉴来的规则要求在交付回合写明的东西；这里它是持久记录的一个字段，而不是回复正文。
- 取代链在写入之前判定，判据取自日志本身。产物必须在磁盘上存在（日志记事实，不记计划）；`撰写` / `修订` 轮不得复用日志已登记的路径，因为那是原地覆盖，规则要求的是新文件加一条 `supersedes`；`supersedes` 指向的路径必须已在日志中出现，否则就是凭空的引用，会扯断它本要承载的链；同一旧版不得被取代两次，因为取代链是一条线而不是分叉。被拒的一轮会在一则消息里列出全部缺陷，各带稳定的规则 id 与修法。
- 该条目就是案件的本轮记录，因此先于渲染：`patent.patch.yml` 把 `matter_log_append` 加进 `render_patent_document` 与 `build_patent_filing` 的 `deliveryGate` 前置项。缺少本轮条目的回合交付不了自己的交付件——调用被拒，拒绝消息点名所缺的这一步。
- 执行点是交付门禁，不是回复。回复级扩展点确实存在：`agent/turn-stopping` 是回合边界的串行钩子，监听者调用 `agent.steer(...)` 后，状态机会重读收件箱并在同一回合再跑一步（`hooks-claude-code` 就是这样给自己的强制续跑设上界）。这里有意不用它，理由见第一条替代方案。
- `scripts/verify-preset-tool-refs` 现在把 preset 自身 `deliveryGate` / `structuralGate` 声明里携带的工具名一并解析到已挂载工具集上，不再只看反引号里的散文引用。前置项点名一个没有任何已挂载包注册的工具时，每个会话里被门禁的调用都会被拒，而声明本身仍然是一段合法的 YAML——这是唯一能让其余检查全绿的门禁缺陷。

## Alternatives considered

- **对交付回合正文做回复级检查（`agent/turn-stopping` + `agent.steer`）。** 这是借鉴规则的原本形态——一个固定标题，缺了即视为本轮未完成——而且可实现。它落选的原因是：执行它意味着用标题约定去判定自由回复正文，还要把范围限定在产出过交付件的回合，并且每当判定说不就要多付一步模型调用；该规则要保护的那些持久事实改由门禁承担，确定性地、每会话一次。
- **扩展 `verify_deliverable` 接受取代关系**（对标清单给的另一条落点）。它已在核对案卷主路径与交付版是否一致。它不能当门禁的前置项，因为它读的是渲染产物，而被门禁的调用跑完之前渲染产物并不存在，于是它只能继续是自愿调用的——本 preset 自己的注释就记着自愿交付工具的处境：13 个渲染过交付件的会话里，只有 2 个在首次渲染前跑过 `rule_check`，`law_verify` 一次都没跑过。
- **对交付工具的结果文本做规则资产。** 结果文本是工具自己的输出；日志是模型写的文件，所以任何作用于结果文本的规则都看不见本轮是否留过档。
- **把既有约定写得更严格。** 日志本来就是这样。对标清单之所以有这一项，正是因为该约定没有执行点。

## Consequences

- 日志有了唯一写入口与固定字段集。模型不能再手写条目；工具不接受的条目会在调用处失败，而不会以某种后人读不出结构的形态落地。
- 门禁的台账按 agent 记录本会话内成功返回的工具名，因此一条条目即满足本会话后续所有被门禁的交付。下限是「本会话在出件前留过档」，不是「每次渲染各有条目」；按轮计数需要把台账改成按回合作用域，那会连 `rule_check` / `law_verify` 两条前置条件一起收紧。
- 本次改动之前写下的日志仍然可读。非本工具写的条目不会被解析为结构化条目，而取代链判定仍看得见这些行携带的路径，因此更早建案的案件可以取代旧版产物——也不能把旧版悄悄当成新一轮的产物复用。
- 新增工具的代价：`patent-oa-response` 的 schema 侧车增加 59 行，两个交付工具各增加一个前置项名。

## Testing

- 单元（`packages/patent/patent-tools/tests/matter-log-append.spec.ts`，19 例）：渲染经解析往返，自由文本内含 `|` 与 `、`；每个判定器都各有自己的反例（产物缺失、原地覆盖、取代项未知、取代链分叉、复用路径），而交付轮可以再次引用前一轮的路径；追加后既有字节仍是前缀；被拒的一轮不写任何东西；案件目录内的路径无论以何种写法传入都按案件相对路径存。
- 门禁机制（`packages/patent/patent-rule/tests/delivery-gate.spec.ts`）：按 preset 的前置项清单，在另外两道闸门都跑过之后仍因缺 `matter_log_append` 被拒，拒绝消息点名它；它成功返回后放行。preset 自身的声明由 `packages/bundle/web-app/tests/patent-preset.spec.ts` 断言，`scripts/verify-preset-tool-refs.spec.ts` 新增四例覆盖门禁名解析（前置项未挂载、一对已挂载、被禁用的行）。
- 录制会话：`pnpm run test:snapshot:refresh` 恰好重写一个侧车（`snapshots/session/patent-oa-response/tool-schemas.expected.json`，即新工具的 schema），`pnpm run test:snapshot -t "patent"` 回放 11 个场景全绿。
