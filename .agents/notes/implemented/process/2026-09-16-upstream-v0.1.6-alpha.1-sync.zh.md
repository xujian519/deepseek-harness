# Agent Note: 上游 v0.1.6-alpha.1 同步与 host 面别名表维护

Status: implemented

[English](2026-09-16-upstream-v0.1.6-alpha.1-sync.md) | 中文

## Problem

本次同步把 fork 的跟踪点从 `dsh-v0.1.5-rc.2` 的同步基点推进到上游 master 上的 `dsh-v0.1.6-alpha.1` 发布。上游前进 666 个提交，fork 自带 495 个，因此首次合并有 122 个文件冲突。

上游增量重命名了两个包族（`code-runtime*` → `ptc-runtime*`，`workflow-worker-thread` → `workflow-ptc`），新增了 `ssh/*`、`computer-use-cua-driver-*`、`browser-use-*`、`lsp`、`mcp/mcp-resources`、`compaction/compaction-image-offload`、`util/lazy-require`、`api/terminal-controller`、`client/ui-sidebar-terminal`、`experimental/auto-review` 等包，把根版本推到 `0.1.6-alpha.1`，加入 `docs/persistence-changes/**` 发布回顾集，为 `SubprocessHandle` 扩出必填的 `control` 通道，收紧 Typert manifest 校验以要求带 `create()` 工厂的严格编解码器，删除 `agent/session-start` 事件并把它的 `source` 字段并入 `agent/created`，新增 `mcp/mcp-resources` 包与作为 MCP 服务器资源与指令注册所有者的 `mcp-client/src/server-context.ts`，回退事务式 Cordis reload（`Revert #932 transactional Cordis reload changes`），并删除 `scripts/verify-vendored-links.ts`。

fork 侧的难点在于：同一个冲突块可以同时装着上游的删除与 fork 的新增，而只统计哪一侧出现哪个名字无法区分二者——可它们的处置方向恰好相反。

## Decision

- **冲突里只出现在一侧的名字本身不构成证据，来源才是。** 本次同步里有两个冲突块的形态按该口径完全一致，裁定却相反。`surfaceInstructions` 只存在于 fork 一侧：fork 的 `packages/mcp/mcp-client/src/index.ts` 把 `inject` 扩成 `['tools', 'systemPrompt']`，把该开关做成两个 transport 变体上的必填字段并以 zod 默认 `true`，再由自己的 `ctx.effect` 块注册 `mcp:${serverName}:instructions`——而 `dsh-v0.1.5-rc.2` 同步基点与 upstream/master 都没有其中任何一项。上游针对同一主题的对应物在本版以一个**新文件**到来：`packages/mcp/mcp-client/src/server-context.ts` 的 `registerServerContext` 把最后一个成功连接的服务器指令文本注册为 `mcp:<server>` 段落，order 取自 `systemPrompt.getSectionOrder('MCP_SERVERS')`，并带 `interpolate: false`。处置是保住 fork 的能力、同时让上游的文件继续做唯一注册所有者——同一个段落名注册两次会相撞——因此并集把该开关穿进上游的注册，并让开关在两个公开 transport 配置上保持必填，延续 fork「由解析后的配置承载该决定」而不让某个构造点默认化的设计。与之相对，`agent/session-start` 是合并基点上存在、上游把 `source` 并入 `agent/created` 后删除的上游事件；fork 唯一的消费者（`openviking`）改为迁移到 `agent/created`，而不是恢复该事件，且那条自己发出该事件名的用例现在改为发活事件名——因为自己发出的事件名不可能暴露已经腐烂的监听器。该迁移之后，被退役的名字在构建产物之外的 `.ts`/`.tsx` 中已不存在，因此未来的合并无法在不弄红用例的前提下悄悄把它复活。
- **host 面别名表保持手工维护。** `tsconfig.base.host.json` 不是可以删除的过期副本：v0.1.5-rc.2 的同步笔记把它记为既定约定（"The host-face alias map stays hand-maintained on each sync"）。本次同步补入 host 面需要的别名（`dsh-ptc-runtime`、`dsh-ptc-runtime-node`、`dsh-client-modules/client`、`dsh-api-terminal-controller`、`dsh-mcp-resources`），删除目标已被重命名消灭的条目，而两条从未悬空、只是指错路径的条目（`api-plugin-market-controller/invariant`、`node-addon-landlock-run`）改为重指向而非删除。
- **事件关系生成器拒绝了导出的分发 helper。** `eventNamesFromParameter` 在 `hasExportModifier(owner)` 上提前返回，使得仓库级调用点索引——`callSitesFor` 正是为这种情况建立的——对导出声明不可达。fork 把 `collectSessionCallbacks` 与 `invokeContainedSessionObservers` 抽成导出的 `observers.ts` 模块，于是 `session/created`、`session/disposed`、`session/event`、`session/flush` 全部零分发者，`gen-doc-graphs` 抛错。这里错的是门而不是 fork：导出函数只能被其它模块调用，恰恰是这道门不该排除的情形。改动去掉导出判断，同时保留 `provenLocalCallee` 决定同文件快路径是否可靠，因此它只增加调用点、不凭空发明调用点，并补一条用例在门被改回时变红。
- **fork 的 Cordis reload 守卫接受上游回退后的语义。** 上游带有 fork 所缺的事务式回退，且合并后的 `vendor/README.md` 第 8 条写明所钉住的「eager, non-transactional」行为。fork 的环检测仍然经 `EntryGroup.update` → `validate()` 生效，非法配置照样被拒且上一棵好树得以保留；变化的只是可观测形态，从拒绝的 `refresh()` 变为一条告警日志。fork 独有的嵌套行碰撞用例现在断言解析结果、告警与保留下来的树。
- **`better-sidebar` 把 v6 世代的 addon 与 v5 的核心配在了一起。** 它在 `@xterm/xterm@^5.5.0` 旁边声明 `@xterm/addon-fit@^0.11.0`，于是 pnpm 的虚拟 hoist 目录把 `@xterm/addon-serialize@0.14.0` 看到的 `@xterm/xterm` 解析为 5.5.0——该 addon 不声明 `dependencies` 或 `peerDependencies`，其声明级 `import("@xterm/xterm")` 只能落到 hoist 的那一份——而 `@xterm/headless@6.0.0` 是按 6.0.0 给该 addon 定型的。`packages/api/terminal-controller/src/terminal.ts:40` 因此报 TS2345。版本钉到 `^6.0.0`，与 `ui-sidebar-terminal` 一致，树中只余一份 `@xterm/xterm`。
- **fork 独有的工作区版本跟随发布。** 38 个 fork 包仍写着 `0.1.5-rc.2`，而约束门要求每个包与根版本一致，因此 38 个包一并移到 `0.1.6-alpha.1`，连同唯一镜像自身 manifest 的联动常量（`SIDEBAR_SERVICE_VERSION`）；`code-runtime-python` → `ptc-runtime-python` 与 `workflow-worker-thread` → `workflow-ptc` 两次重命名留下的两个构建残留目录被删除。
- **生成物一律重生成，绝不手工合并——除非构建产物会污染它们。** 配置目录、模块图、客户端 slot 目录、依赖目录、会话格式目录、scoped events、Cordis 目录、tsconfig paths、第三方声明与关系图文档，全部从合并后的树重新产出。持久化目录三件套及其 schema 是**核验**而非重生成：`scripts/persistence-schema.ts` 的 `trackedSource()` 把 `lib/types/**/*.d.ts` 也当作可追踪源，因此在已构建的工作树里生成会把每条记录的源指针改写成构建产物形态、偏离已提交的 `src/*.ts` 形态，而已被接受的内容正是干净检出下的那份。本次同步改为撰写自己的持久化台账条目，确认 fork 自上一个同步基点以来新增的 19 个事件根与 1 个可选事件体属性。
- **混合文档的中文侧随生成后的英文侧经配对推进。** `capability-seams.zh.md` 与 `event-producer-consumer.zh.md` 补上了上游侧从未有过的 fork 段落，`config-catalog.zh.md` 则用三方合并重建，因为冲突解决整份取了上游一侧，丢掉了 fork 自合并基点以来新增的中文行（其中含 `patent`、`better-sidebar`、`plugin-market` 的 fork 独有段落）。配对记录用 `verify-translation-pairing --write` 重新登记。
- **配对门禁本身无法证明结构保真。** `verify-translation-pairing` 对哈希记录过期的配对会跳过结构检查，因此过期记录只会报出「out of sync」。本次同步的结构性证明来自直接调用仓库自身的原语（`translationStructureDiff`、`translationStructureSignature`、`partitionGeneratedRegions`、`hasLanguageSwitcher`、`translationLinkLocaleViolations`），并要求零违例。

## Consequences

fork 现在以桌面端、patent、self-evolve、synapse、plugin-market、openviking、better-sidebar、prompt-cache、ui-document-studio、ui-patent-teams、ui-todo-board 等面完好为前提，承载上游的 v0.1.6-alpha.1 基线。host 面别名表对重命名与新增的包重新正确，并将继续在每次同步手工维护：缺失条目会在 host `tsc -b` 与文档类型检查时暴露。由于过期的配对记录会短路配对门禁的结构检查，任何关于重生成的混合文档配对的结构性结论都需要共享原语，而不是门禁的退出状态。上游删除了 `scripts/verify-vendored-links.ts`，而它是 fork「每个 vendored 名字都解析到工作区链接」这一不变量的唯一守卫；树中没有任何地方引用该脚本，也没有其它门禁接手该检查，因此该不变量在有人恢复它之前处于无守护状态。`agent/session-start` 的移除还展示了下一次同类断裂的形态：监听一个上游已退役事件名的监听器之所以能编译，只是因为事件映射容忍它，所以 host 面构建报出一个事件名时，应当去找被取代的名字，而不是去找缺失的别名。持久化生成器带着一个本次同步发现、并有意不修的陷阱：由于 `trackedSource()` 接受 `lib/types/**/*.d.ts`，在已构建的工作树里做任何重生成都会改写目录记录的源指针并报出假差异，因此这些产物必须在干净树上、或先移除涉事包的 `lib/` 之后再核验；该陷阱与其绕行办法记录在 `docs/TECH_DEBT.md`，而不在本次同步里修复。

## Alternatives considered

- **把 `surfaceInstructions` 按 fork 原样恢复、并删除 `agent/session-start` 监听器（即把 fork 自己的注册块贴回来）。** 否决：上游的 `server-context.ts` 现在拥有该段落的注册权，再注册一次会相撞；而两种情况只在来源上不同，裁定方向却相反。该开关作为 fork 的贡献被保留并穿进上游的注册；`agent/session-start` 是上游用更宽载荷替换掉的上游事件，因此其消费者迁移。
- **保留 fork 的段落名与 order（`mcp:<serverName>:instructions` @ 155）。** 否决：fork 的笔记是在当时那个带宽占用格局下论证 155 的，而上游此后把 MCP 服务器上下文做成了自己的具名槽位（`getSectionOrder('MCP_SERVERS')`），且位于拥有注册权的那个文件里。保住 155 等于每次同步都要去补一个上游拥有的文件，只为守住一个不带来任何能力的提示词排序偏好；因此改为修正 fork 的笔记对，使其描述当前契约。
- **删除 `tsconfig.base.host.json`，直接扩展 `tsconfig.base.json`。** 否决：上一版同步笔记已把该文件记录为有意接受维护成本的手工 host 面映射表，且 host 程序确实通过各自的包级 `tsconfig.host.json` 引用解析 client 面子路径，一个排除全部 client 别名的 host 映射表描述的将不是实际存在的 host 程序。
- **把 fork 的环校验重新挂到上游的 refresh 窗口，让 `refresh()` 重新拒绝。** 否决：上游有意回退了事务式 reload，重新拒绝等于在同步里把它翻回去。守卫仍然拒绝非法树，上一棵好树仍然存活，保护完整，只是可观测形态变了。
- **为免动上游测试文件，把解析后配置上的 `surfaceInstructions` 改为可选。** 否决：解析后的配置承载的是 schema 默认出来的决定，可选字段会让某个构造点静默丢掉该开关；改为让那两处构造 transport 配置的上游用例显式写出该开关。
- **整份取上游的中文目录、把 fork 段落延期。** 与前两次同步一样否决：上游中文侧缺掉全部 fork 独有段落，而 fork master 上已审校的译文可以机械前向合并，延期只会让文档门禁持续变红，换不来任何翻译收益。
- **为 `@xterm/addon-serialize` 再加一条 `@xterm/xterm` 解析规则。** 否决：偏斜源于 `better-sidebar` 把 v6 世代的 addon 与 v5 核心配对，在别处钉版本会让某个客户端留在一个它自己的 addon 已经不匹配的核心上。

## Testing

`pnpm run typecheck`（Host `tsc -b` + tsdown，Client `tsc -b`）、`pnpm run lint`、`pnpm run duplication`、`pnpm run test:docs`、`pnpm run doc-sync`、`pnpm run constraints`、`pnpm run hygiene`、`pnpm run verify-package-dependencies`（69 个包）、`pnpm run verify-translation-pairing`、持久化各门禁（`verify-persistence-catalog`、`verify-persistence-changes`、`verify-persistence-formats`、`verify-persistence-releases`），以及受影响的包测试套件，包括 `packages/mcp/mcp-client`、`packages/memory/openviking`、`packages/client/better-sidebar`、`packages/experimental/ptc-runtime-python`、`packages/core/session`、`packages/session/session-persistence-jsonl`、`packages/boot/app-boot` 与 `scripts/gen-doc-graphs.spec.ts` 的门禁用例。事件关系修复的验证方式是：先恢复 `hasExportModifier` 门并观察到新用例失败，再移除它并观察到通过。双语配对用 `verify-translation-pairing --write` 重新登记。该次重录前先做了逐侧漂移审计：44 条过期记录中 40 条两侧都动过，另 4 条——`patent` 预设的 README 与三篇 patent 笔记——只有英文侧动过，原因均是禁词换成了点名确切实段的措辞。这四篇的中文侧都逐句对照过新英文、所述事实相同，故一并重新登记；若单侧漂移的动侧属于重译，则必须先带上另一侧再登记。另有 24 对相对 fork `master` 只有英文侧变动、而中文侧与 `upstream/master` 自己的版本逐字节相同；那属于上游自身的双语状态——上游做完词汇清理后重新登记却未在中文侧跟随——故 fork 随附而非单方面偏离。
