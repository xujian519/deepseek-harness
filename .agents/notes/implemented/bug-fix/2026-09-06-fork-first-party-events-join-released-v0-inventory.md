# Agent Note: Fork first-party events join the released-v0 frozen inventory

Status: implemented

English | [中文](2026-09-06-fork-first-party-events-join-released-v0-inventory.zh.md)

## Problem

Fork first-party events — the `patent-teams/*` team records and `self-evolve/reflection` — are generated by this fork's own plugins and are known to the current build's `KNOWN_SESSION_EVENT_TYPES`, so they must survive into v2. But the frozen released-v0 inventory (`RELEASED_V0_EVENT_DISPOSITIONS` in `packages/session/session-format-v0-to-v1/src/dispositions.ts`) never declared them. The v0->v1 identity edge refuses every unknown non-ignorable event (`assertArtifactCoordinates`), so any real session containing a non-`ignorable` instance of these types could not be migrated and the desktop app reported 「历史加载失败」. After the `todo/write` tags fix, this cluster was the remaining inventory-vs-schema gap that blocked stored history.

`patent-teams/*` are written with `ignorable: true` ([history](../../implemented/bug-fix/2026-08-27-patent-teams-ignorable-session-events.md)), but instances recorded before that envelope convention settled, and `self-evolve/reflection`, carry no marker; a session holding even one such required event is refused across the whole chain.

## Decision

Add the fork events that the data actually contains to the frozen inventory, keyed by their exact payload-member sets, and give each a payload-semantics case so the validator's throw-on-default branch is not hit.

- **`dispositions.ts`** gains `patent-teams/member-added`, `member-removed`, `message-sent`, `task-created`, `task-gated`, `task-updated`, `task-validated`, `team-created`, and `self-evolve/reflection`. Each `required`/`optional` split mirrors the event's own type definition exactly.
- **`payload-validation.ts`** gains one `case` per added event, aligned with the owning invariant's checks (identity as non-empty strings, `ts`/`score`/`confidence` finite numbers, `attempt` safe integer, arrays of strings, booleans) and no stricter.
- Because `RELEASED_V0_EVENT_TYPE_SET` is the `Object.keys` of the inventory, these events are now admitted by both the v0->v1 and v1->v2 coordinate checks at once. They are also no longer treated by `isIgnorableUnknown` as external events worth dropping: an `ignorable` instance of a type now in the inventory is retained, which is correct for build-known first-party records.

`patent-teams/team-deleted` is deliberately omitted. The stored data holds only `ignorable` instances; the author-declared "safe to omit" meaning already applies, so the v0->v1 admit + v1->v2 drop path is the right one, and adding it would wrongly preserve records meant to be dropped. The other `self-evolve/*` events (`start`, `mined`, `proposed`, `validated`, `commit`, `end`) are also omitted: zero instances exist in stored history, and their payloads embed not-fully-confirmed nested objects, so adding them risks encoding guessed fields the way the original port did.

## Alternatives considered

- **Relax the validator to admit unknown non-ignorable events.** Rejected: it would mask a real inventory-schema gap and lose the loud-failure boundary for genuinely external required events.
- **Keep the alpha refusal.** Rejected: it is the bug itself — stored history with fork events cannot open at all.
- **Remove these events from `KNOWN_SESSION_EVENT_TYPES` / mark them ignorable at write time.** Rejected: they are first-party records, and degrading them to droppable would discard real state.
- **Add `team-deleted` and the other `self-evolve/*` events too.** Rejected: no non-ignorable instances exist to justify retaining them, and the unconfirmed nested payloads make an exact inventory guess risky.

## Consequences

Full replay across all 404 stored v0 sessions now migrates 388 to v2 successfully. The remaining 16 are genuine data corruption, not schema: sessions interrupted mid-tool-call leave an unclosed `tool/call` (`step/end leaves unresolved tool call`), a broken sequence gap, a `turn/start` that does not open the expected turn, or a `tool/result` that is not the exact `TOOL_NOT_STARTED` repair. The validator rejects these correctly, so they are out of scope for this change — making the migration accept them would hide a real bug. The `RELEASED_V0_EVENT_TYPE_SET`-length assertions in `validation.spec.ts` were updated to the expanded inventory.
