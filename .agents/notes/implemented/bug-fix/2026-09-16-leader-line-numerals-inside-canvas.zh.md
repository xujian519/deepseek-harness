# Agent Note: 引线标号落在附图画布之内

Status: implemented

[English](2026-09-16-leader-line-numerals-inside-canvas.md) | 中文

## Problem

`generate_patent_figure` 对框图与组件层级图默认用引线绘制参考标号（SVG 下这两类图型 `leader_lines` 默认开启），`add_patent_figure_references` 对调用方提供的 SVG 提供同一套放置能力。标注器从每个节点组 `<g class="node">` 读出轮廓，然后把标号与其 `<line>` 引线插在 `</svg>` 之前。两处缺陷使这份输出里的标号根本没有渲染出来。

Graphviz 把节点几何表达在外层 `<g class="graph">` 组的坐标系里——`dot` 15.1.1 输出 `transform="scale(1 1) rotate(0) translate(4 40)"`——而注入的引线组位于文档根元素、在该组之外。于是每条引线与每个标号都被组平移整体偏移：在一个三块横向排列的夹具上，标号落在它所标注部件上方 40 pt 处，且与轮廓脱离。

放置逻辑同样无视根元素声明的画布。SVG 会裁掉 `viewBox` 之外的内容，因此最右部件的标号（同一夹具上 363 pt 画布里的 `x` 368.4）以及所有纵坐标落到画布之上的标号完全没有渲染。调用仍然返回成功且 `warnings` 为空数组，光栅化结果与同一张图用 `leader_lines: false` 生成的结果逐像素一致。

放置修正之后又暴露出第三处缺口：候选位置只与节点轮廓和其他标号比较，于是在横向链上，右侧引线与向外的连接线共线，看起来像连接线箭头的一部分，而不像引线。

## Decision

**放置改在根坐标系中完成，画布按放置结果扩边，图内已绘线条视为障碍。**

- `groupScopes` 遍历全部 `<g>` 作用域并累计各作用域到根坐标系的平移；`frameAt` 解析指定文档偏移处最内层的帧。节点轮廓、边路径、箭头与边标签框在做任何几何判断之前都先换算到根坐标系，因此嵌在 cluster 内或位于带平移的图形组下的节点也能正确放置。帧含缩放、旋转、翻转或无法解析的变换时不给出帧：该节点的标号内嵌进部件名，并由调用结果报告。
- 引线线段与标号文本框都必须避开三类障碍：节点轮廓、已放置的标号，以及边绘制的内容——采样成折线的 `<path>` 贝塞尔曲线、箭头多边形，以及按 `font-size`、`text-anchor` 与逐字宽度（CJK 按满宽、其余按窄宽）估算的边标签框。共线重叠也算冲突，依据《专利审查指南》第一部分第一章 4.3「剖面图中的剖面线不得妨碍附图标记线和主线条的清楚识别」。
- 放置完成后，`expandCanvas` 把已放置的矩形与根元素声明的 `viewBox`/`width`/`height` 比较，在每一处越界侧补 2 个用户单位的安全边距：右、下越界放大尺寸属性，左、上越界把 `viewBox` 起点外移，使图面本身不产生位移。根元素没有 `viewBox` 时按其 `width`/`height` 合成一个（长度单位换算为 px，因为无 `viewBox` 的画布其用户单位就是 px）。尺寸值无法换算（百分比、缺一个轴、非正数或不可解析）时跳过扩边，而不是猜测。

## Alternatives considered

**把整份文档换算到根坐标系。** 改写每个元素的坐标可以彻底消除坐标帧问题，但它改动了标注器并不拥有的内容（包括调用方提供的 SVG），且漏掉一个元素就会悄悄破坏图面。只换算标注器推理所必需的几何、并把引线组输出在根元素，把改动面收敛到根标签的画布属性与注入的那一个组。

**在 DOT 里预留空间（`margin`、占位 rank 或不可见节点）。** Graphviz 的 margin 能预先开出空间，但无论本图是否需要标号都要付出同样的空白带，无法覆盖四个锚点方向与不定的标号长度，并且比标号实际所需更多地压缩提交页尺寸内的图面。

**把引线组注入图形组内部**，让它按构造继承坐标帧。这能修正放置却修正不了可见性：画布比较仍然需要该组的平移，而且注入的组会先于它之后的兄弟元素（边）绘制，把引线压在它本应避开的线条下面。

**在坐标帧运算里支持缩放、旋转与翻转。** 完整的仿射换算可以实现，但翻转会反转上/下锚点的语义与文本基线偏移，而 CLI 渲染器面向的 Graphviz 15 只输出纯平移。退化为内嵌标号并给出警告，能让这一限制可见，而不是去猜几何。

**把文档里每个 `<path>` 与 `<polygon>` 都当成障碍。** Graphviz 自己会画一个覆盖整幅画布的白色背景矩形，这条规则会否掉所有候选、把每个标号都逼成内嵌形式。把障碍限制在 `<g class="edge">` 组上，与节点解析使用同一类结构标记。

## Consequences

- 引线标号真的产出可见标号：部件与标号的对应关系出现在图面上，而不只是出现在 `numeralMap` 与面向模型的文本里。
- 声明的画布可能比 Graphviz 产出的布局更大，多出引线长度、标号宽度与每个越界侧的安全边距之和。与提交规格的 `page`/`size` 属性叠加时，图面可能因此超出配置的页面框；提交级输出请把 `figureMargin` 保持在约 0.5 cm 及以上。
- 密集图上的放置更保守：当边标签或箭头占满四个锚点位置时，标号会被推进部件名（并给出警告），而早先的规则会在线条上画出一条引线。这个取舍是刻意的——宁可内嵌标号，也不要与主线冲突的引线。
- 位于缩放、旋转或翻转折组内的节点改为报告降级放置，而不是画出错位的标号；提供这类 `raw_dot` 的调用方能在 `warnings` 里看到该限制。

## Testing

- `packages/patent/patent-tools/tests/figure-leader-line.spec.ts` 覆盖坐标帧换算（多层与 matrix 平移、不可换算的变换）、边与边标签避让，以及扩边的每个分支：仅有 `viewBox`、按 pt 尺寸合成 `viewBox`、尺寸不可换算、左上越界。
- `packages/patent/patent-tools/tests/figure-svg-annotate.spec.ts` 覆盖放置契约与左右越界两种扩边；`packages/patent/patent-tools/tests/figure-graphviz-real-render.spec.ts` 在真实 WASM 与 CLI 引擎上跑同一条链路。
- 三块夹具在改动前后都用 `rsvg-convert` 光栅化过：改动前标注结果与未标注渲染逐字节一致；改动后每个标号位于其部件外侧、引线触及轮廓，且没有引线压在连接线上。
