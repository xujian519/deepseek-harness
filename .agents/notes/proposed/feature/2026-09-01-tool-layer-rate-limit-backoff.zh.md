# Agent Note: 在工具层处理提供方限流，而非靠模型 sleep

Status: proposed

**部分实现（2026-09-01）：** `patent_pdf_download` 的 fetch 兜底已按 Retry-After 退避重试 429/503，并返回类型化限流提示（`networkErrorCode` / `retryAfterMs`）。按提供方区分的限流信号检测，以及取消/退避上界的测试仍属前瞻。

[English](2026-09-01-tool-layer-rate-limit-backoff.md) | 中文

## 问题

在 `dsh-session-b300a460` 中，researcher 成员（关键路径第一棒）共发出 11 次 `sleep`，合计 15.8 分钟——从 `sleep 20` 到 `sleep 300`，大多标注为「等待 Google Patents 限流」。直接 `curl` 访问 `patents.google` 触发 HTTP 429 限流，模型便通过在 `bash` 调用里手写指数退避来应对。针对此类工作已存在的一类工具——`patent_search`（平均 2.3s）、`patent_metadata`（平均 0.9s）、`patent_pdf_download`——虽然被使用，但下载路径仍七次回退到裸 `curl`。

这造成一种由模型发明、以墙钟 sleep 写成的限流恢复策略，约占关键路径成员总时间的 40%，且与提供方自身的 `Retry-After` 信号无关。

## 提案

由工具层负责限流处理。当提供方返回限流信号（HTTP 429 及 `Retry-After`，或提供方特定的限流标记）时，工具暴露一个携带该 retry-after 的类型化结果，运行时以有界的指数加抖动退避进行重试——或返回一个显式的「throttled, retry-after」结果——而不是产出一个会让模型用 `sleep` 命令去回应裸错误。恢复等待有界且遵从取消信号，调用方收到最终结果或类型化的限流结果。当一类工具已覆盖该操作时，运行时不应怂恿用会重新引发限流的裸 HTTP 变通方案。

## 考虑过的替代方案

- **返回裸错误并让模型 sleep。** 即当前行为；不确定、忽略 `Retry-After`、浪费模型书写的墙钟时间。
- **模型层重试循环。** 与 sleep 同样漂移且不确定，还要额外提示成本。
- **每个提供方固定等待。** 忽略提供方自身的 retry-after，不是等待过度就是等待不足。
- **在工具内无界阻塞重试。** 在持续限流下可能挂住调用方，且不遵从取消信号。

## 接受标准

- 被限流的提供方调用返回携带 retry-after 的类型化结果，或有界重试在无需模型参与的情况下完成。
- 总退避有界；调用方不会被无限阻塞，且可被取消。
- 任何限流恢复都不要求模型发出 `sleep` 命令。
- 不同提供方的限流信号按提供方分别检测，非限流错误不会被误判为可重试。
- 测试覆盖 429/`Retry-After` 路径、退避上限、取消以及按提供方的信号检测。

## 风险

在工具内重试会延迟调用方，必须保持在文档化为界内。检测必须区分真正的限流、瞬时网络问题与硬配额，以免错误被无限重试，或永久被「throttled」掩盖。
