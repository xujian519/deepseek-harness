# Agent Note: 目录列出的子项按有界批次并发解析

Status: implemented

[English](2026-09-16-listing-child-batches.md) | 中文

## Problem

`listDirectory` 为每个子项串行执行两次线程池往返——经 `resolveListedChildTarget` 的 `realpath`，再经 `probe` 的 `stat`——严格一次一个子项。每个子项的这两次操作与任何兄弟项都相互独立，因此列出过程同一时刻只用一个 libuv 线程池线程，其成本随「单次系统调用延迟 × 条目数」增长。在 3,200 条目的目录上于本机热缓存文件系统实测：83.6 ms，即每条目 26.1 µs。在单次操作延迟占主导的文件系统上（冷缓存、网络挂载、虚拟化磁盘），同样的串行形状的成本是「延迟 × 2 × 条目数」。

## Decision

- 子项按 `LIST_BATCH_SIZE`（32）分批，每批一次 `Promise.all` 解析，使一批之内的线程池往返相互重叠。批次上界既让 libuv 线程池保持繁忙，又不会把整个大目录的操作一次性排入队列。
- 条目仍按 `localeCompare` 名称序落位：批次是已排序数组的切片，每批结果按序追加。
- 逐子项的错误映射不变：解析或探测失败的子项仍抛出 `listingIoError` 并指明该子项的显示路径。
- 取消在每批之前与最后一批之后各检查一次，因此中止粒度从「一个子项」变为「一批子项」。

## Alternatives considered

- **直接用 `readdir` 已返回的 `Dirent` 类型，只对文件做 stat。** 已否决：会改变 `FsDirEntry` 语义——指向目录的符号链接会从 `directory` 变成 `other`，指向文件的符号链接会丢掉 `size`。
- **对全部子项用一次 `Promise.all` 并发解析。** 已否决：10 万条目的目录会一次性排队 20 万次线程池操作，把延迟问题换成内存与队列深度问题。
- **新增 `maxEntries` 参数并把列出分页。** 已否决：这是文件系统能力接缝上的新公共 API，而该接缝按设计排除分页。

## Consequences

在同一个 3,200 条目的目录（3,000 个文件、200 个目录）上于本机热缓存文件系统实测：

| 形状 | 成本 |
|---|---|
| 逐子项串行（改动前） | 83.6 ms（每条目 26.1 µs） |
| 批宽 4 | 45.5 ms |
| 批宽 8 | 32.1 ms |
| 批宽 16 | 24.3 ms |
| 批宽 32（本次实现） | 18.5 ms |
| 批宽 64 | 17.2 ms |

真实 `listDirectory` 实测 20.9 ms，对照串行的 83.6 ms。批宽在 32 与 64 之间已不再有收益，而批越宽中止等待越久，32 正是两者的交汇点。
