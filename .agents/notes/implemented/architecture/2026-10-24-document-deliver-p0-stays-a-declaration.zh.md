# Agent Note: 文档 P0 质量门保持声明，不设为执行点

Status: implemented

[English](2026-10-24-document-deliver-p0-stays-a-declaration.md) | 中文

## Problem

`document_deliver` 接受 `gate.p0`，即模型自述已核对的质量门技能稳定 id 列表（`P0-1` … `P0-6`）。关于这份列表，有三处说法互相矛盾：参数 schema 称它为「已通过并核验的 P0 自检项」，并告诉模型「P0 全过才允许登记」；工具大描述称核验结论与「P0/P1 自检项」并列写入；而实现只记录该列表，并不核验。模型读 schema 会以为工具在核验这份声明，审阅者读同一段文本也会得出同样结论。两者都不成立，而交付工作室把两列并排渲染，于是操作员带进交付复核的正是那个错误理解。

同一处矛盾还引出了一项具体的设计提案：若某次登记的 `p0` 未点名全部六个 id，就拒绝该登记。这个提案表面上是一次收紧——说不清自己清单的交付物不该登记成功——本笔记正是为回应它而写。它败在 id 能证明什么这一点上。

## Decision

**`document_deliver` 记录 P0/P1 声明，从不核验它。** 参数描述说明：这些 id 是模型的自述，工具把它们与自己产出的确定性核验结论并列记录，漏填或写法无法识别的 id 以登记提示返回，而非拒绝登记。工具大描述与 README 口径一致：是否拒绝登记只由机器可判定的核验结论决定，覆盖残余占位符、未声明的锚点、空章节、所选风格的禁用词与声明的字数预算。P0 声明是否属实是审阅者的问题，不是工具的问题。

**列举不是门，以列举不全为由拒绝也不会造出一道门。** 要求六项 id 齐全，只证明模型填了六个字符串，与这六个 id 所指代的六件事无关：命名是否合规范、文件是否自包含、来源是否标注。id 是陈述所用的词表，六项齐全与只填两项同样可信。真正能拒绝交付的核验已在内容上独立执行，并会因阻断级问题拒绝登记。再加一道 id 完整性拒绝，等于在它前面放一道更弱的拒绝，并诱使模型去满足列表而不是去满足文档。

**把声明门控在自身上，不判定任何东西。** 门禁把一个前置条件绑到后一次调用上。`patent` 模式的两个部分都成立：前置条件是中间动作（该轮的规则、引用与归档运行），被门控的调用——`render_patent_document`——是本域唯一被认可的生产路径，因此拒绝它就真的拦住了任何通路上的交付件。文档模式两个部分都不成立。字节先由任意通路写出：手写 Markdown 与 HTML、`render_doc_template`、`officecli` 用户级技能出 `.docx` 与 `.pptx`。登记是终局声明——其后不再调用任何工具——所以拒绝它不改变任何文件，也不拦住任何交付；交付件已经存在，会话无论如何都会结束。那里的拒绝只是去掉了交付工作室与后续复核要读的那条日志记录，这严格劣于记录一条看起来明显就是声明的声明。

**未知 id 的通路也点名全部缺失项。** 只填无法识别词语的调用，此前只报出落空的写法，于是一行回执读起来像少了一项，实际少了六项。现在只要有任何 id 缺失，`p0ChecklistWarnings` 就输出完整的缺失列表，无论其余条目是什么。回执保留未知 id 那一行——落空的写法——再补上点名全部六项的那一行。「一之六」与「六之六」在会话记录里是同一个计数，却是关于这次交付的不同主张，这正是仅凭计数无法承载的原因。

三处表述现在同一条规则：工具大描述、`gate` 与 `p0` 参数描述、README 都写明声明是被记录而非被核验，预设 persona 写明 P0 由模型自己核。

## Alternatives considered

**当 `p0` 漏填 id 或点名未知 id 时拒绝登记。** 即本笔记回应的提案。它衡量的是声明的拼写而非文档本身，而且会把模型训练成产出六个字符串——那是通过检查最廉价的方式——真正会拒绝交付的内容核验则分毫未变。它还有重放代价：已录制的 `document-deliver` 场景登记 `gate.p0: ["命名规范"]`，一个未知写法，正是为了让猜错写法的模型学到 id 而不丢掉这次登记。

**在工具里核验 P0 各项。** 每一项都是关于文档用途的判断——这个名称对其受众是否约定俗成、这是否就是预期的来源——而工具读的是字节，不是意图。可机械判定的部分已经拆成各自带结论的独立核验，核验其余部分等于凭空造出第二种更弱的意见，并把它与真实结论并列展示。

**把登记门控在「本会话已跑过核验」上。** 这是 `patent` 模式中奏效的形态：由 `tools/post-execute` 填充的台账记录哪些前置运行成功过。它不可移植：文档核验内在于 `document_deliver` 自身、每次调用都跑，因此没有一个独立前置可被观测缺失，而将被门控的工具正是持有核验的那个。

**保留 schema 措辞，只澄清 README。** 否决：schema 是模型在调用时读到的、也是审阅者在录制请求头里读到的文本。别处的散文纠正不了一句称工具会核验该列表的描述。

## Consequences

- 交付回执把自述的 P0/P1 项数与工具自己的核验结论分成两列。任一列都不蕴含另一列，工作室两列都展示。
- 点名未知 id 或漏填 id 的模型会被告知词表是什么、还有什么未陈述，登记仍然成功。会话记录保留该声明，后续复核能看到这份声明是不完整的。
- 本模式没有任何东西阻止会话在交付物未登记或未核验的情况下结束。这一缺口记录在设计选择之处，而非在此关闭：本模式 README 写明所报核验不是一次评审，并写明要设门需要一次交付终结调用，而不是加在这个调用上的条件。
- 这些措辞是模型可见文本，被两个免 key 快照钉住：`snapshots/session/document-deliver/`（`document_deliver` schema 旁文件与录制轮次产生的回执）与 `snapshots/web/legal-preset/`，后者的预设挂载同一个插件，因而钉住同一份 schema。这些描述中任何一处变动，都会让两次重放失败，直到旁文件被刷新。
