# Agent Note：检索质量的度量门，语料自撰于仓库内

Status: implemented

[English](2026-10-13-retrieval-quality-metric-gate.md) | 中文

## 问题

`patent_eval` 的 `retrieval` 模式把"检索式含三个及以上词条"记为满分，而各处都把这个分数叫 `检索覆盖度`。它从不读结果列表，因此这个数字描述的是检索式的形态，读起来却像是对背后检索的评价。仓库里也没有任何地方记录过 BM25 检索到底把回答该查询的那篇文献排在第几条——于是一次检索改造（换索引、加召回、加精排）既没有验收标准，也没有回归底线。

2026-09-30 的对照报告（`2026-09-30-patent-domain-external-benchmark.md` 的 P1-6 项）点出了这个缺口，也给出了修法的形状：主指标是首次命中的位次，BM25 是任何改进都必须打败的基线，资产要放在仓库内而不是借用数据集——候选的两套数据集分别带着未证实的下载条款与非商用许可。

## 决定

- `@deepseek-ai/dsh-patent-tools` 新增 `src/eval/ir-metrics.ts`：主指标 `rankOfFirstRelevant`，它的跨查询聚合 `meanReciprocalRank`，以及用于分级相关度的 `ndcgAtK`。三者都是纯算术——不检索、不读盘、不调模型——由本包作为库发布。不新增模型可见工具。
- 语料是仓库自撰的：12 篇中文短文与 10 个查询，判读带相关度等级，放在 `tests/fixtures/retrieval-corpus/`。术语分布是刻意安排的——若干文档重复同一术语、或共用同一句模板话术——所以基线会出现真实的词频假阳性，而不是每个查询都把判读为相关的那篇排到第一条。
- 基线排序是**测出来的**，不是写出来的。`bm25-baseline.json` 记录的是 FTS5 索引实际产出的排序：`tokenize=trigram`，MATCH 表达式由引号短语 OR 组合，`ORDER BY bm25`。这正是 `dsh-patent-knowledge` 检索所用的栈，夹具还复用了本包之外那套 `joinFtsOrTerms` 与 `sqliteHasFts5` 助手，使记录的基线与它所代表的引擎不会各自漂移。词条都在三字符及以上，因为 trigram 索引无法匹配更短的词；引擎对短查询的 LIKE 降级不在本夹具范围内，夹具里写明了这一点。
- 测试断言三件互相独立的事：记录的排序仍可由 FTS5 复现；指标能从该排序复算出记录值；以及这把尺子**有判别力**——把每个查询里判读为相关的文档全部推到末尾后，任何有命中的查询都不得变得更好，且聚合 MRR 必须明显下降。没有最后一条，这个模块就只是一台没人校对过的计算器。
- `patent_eval` 的检索维度改名为它实际度量的东西（`关键词条数`），模式标签与明细行也改成"只判检索式形态"。判分行为一字未动，因此该模式仍是它一直以来的形态检查；变的是它不再自称 `检索覆盖度`。

## 考虑过的替代方案

- **借用第三方数据集。** PatentMatch 正是"权利要求 ↔ 对比文件"排序想要的金标准，Patent-CE 提供执业专利律师标注的五维对比。两者都输在条款上：PatentMatch 的下载与使用条件未获证实，Patent-CE 是 CC BY-NC 4.0，不能与商用产物同批分发。仓内语料无法按大规模人工判读标定，这个代价写进了 README，而不是藏在一个数字后面。
- **从 BM25 自身派生相关性判读** —— 把引擎排第一的那篇标成相关。那样得到的基线是 MRR 1.0，什么都没度量。
- **用 TypeScript 实现 BM25，让夹具不依赖 SQLite。** 重写一遍等于给被测对象第二个定义，而记录的排序必须来自真正服务检索的那个引擎。
- **新增模型可见的 `retrieval_eval` 工具。** 这套指标是给仓库自己验收检索改造用的；模型可见工具会为一个没有模型调用需要的检查增加 schema、渲染结果与会话事件。
- **只改维度名、留下模式标签。** 标签是结果的第一行（`检索覆盖度评分`），也是整个面里最不准确的名字。

## 后果

- 语料小且自撰，所以它的基线是回归底线，而不是"检索已经够好"的证据。十个查询里有两个 BM25 直接漏检，另有两个把不相关的文献排在相关文献前面；这两个数字都来自夹具刻意安排的术语重叠，也正是它具备判别力的原因。
- 基线复现那一段在运行时 SQLite 没有 FTS5 时跳过——`dsh-patent-knowledge` 早已为捆绑版 Node 的这一情形降级。指标算术、语料闭合检查与判别力检查在任何环境都跑。
- `patent_eval` 的 `retrieval` 输出变了（维度键与模式标签）。分数一模一样；一个快照 sidecar 与生成的工具目录随之重录。
- 后续检索工作有了唯一一处可被度量的地方；指标函数从 `patent-tools` 发布，更大的基准可以直接建在它们之上，不需要新的接线。

## 测试

- `tests/ir-metrics.spec.ts`（8 例）：每个指标都有可手算的锚点（相关文档在第 3 位时 nDCG@3 = 0.5；交换两条分级相关文档后 nDCG 下降；按 k 截断）；漏检返回 `null` 与 0，且 MRR 的均值把漏检计入分母；语料闭合（12 篇文档、每个词条不短于 trigram 下限、判读指向存在的文档、每个查询都有基线记录）；每条记录的排序经 FTS5 复现；每个记录的指标值被复算核对；以及判别力检查——退化的 q09 首次命中落到第 4 位，聚合 MRR 至少低 15 %。
- `pnpm exec vitest run packages/patent/patent-tools`：1332 通过、2 跳过，其中包含随维度改名一起改的两处断言。
