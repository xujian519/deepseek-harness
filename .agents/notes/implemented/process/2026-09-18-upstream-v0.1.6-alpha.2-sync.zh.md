# Agent Note：上游 v0.1.6-alpha.2 同步，以及构建产物对源码的遮蔽

Status: implemented

[English](2026-09-18-upstream-v0.1.6-alpha.2-sync.md) | 中文

## 问题

fork 从上游的 `dsh-v0.1.6-alpha.1` 推进到 `dsh-v0.1.6-alpha.2`。上游前进 887 个提交，fork 自带 529 个，因此首次合并冲突 101 个文件。上游重写了 `apps/desktop` 与 `apps/desktop-host`（以 `runProfile` 加 IPC 加本地端口取代无端口协议与 `desktop.cordis.patch.yml` 叠加层），把 `dsh plugin` 转发移入 `@deepseek-ai/dsh-plugin-manager`，把 `tool-present` 包从 `fs` 分组移到 `deliverables`，以 `uiWorkspace.openSession` 取代 `ISessions.open`，并以 `retainedBy` 映射取代 `SessionListState.current`。

本次同步有两类失败并非来自冲突，而是来自工作树。合并树上 18 个单测文件失败，其中整个客户端簇都指向「与 TypeScript 源码并排存放的已编译 JavaScript」：`DEBUG=vite:resolve` 显示 `@deepseek-ai/dsh-client-ui-renderer/client` 解析到渲染器 `src/client/` 目录下已编译的 `index.js`，随后又链入同目录的 `registry.js`、`scoped-slots.js` 与 `app.js`。

## 决定

- **桌面族采纳上游重写，fork 逐项回移自有能力。** 上游新的 `apps/desktop/scripts/electron-builder-config.mjs` 工厂取代了 fork 的配置，因此 fork 的品牌图标选择（`iconFile`、`assets/` 默认值、`DSH_DESKTOP_ICON_DIR` 覆盖项）、其 unsigned darwin 构建（`darwin` 下的 `DSH_DESKTOP_UNSIGNED`、`dmg.sign: !unsigned`、`mac.identity: null`、`mac.notarize: false`）以及其对打包目标限制的放宽（`--unsigned` 适用于 Windows 与 macOS 目标，而非仅 `win-x64`）都迁入该工厂。上游的强制更新策略随后要求一个 HTTPS 部署源，因此 fork 的图标与 unsigned macOS 用例在其余发布输入之外补上 `DSH_DESKTOP_MANDATORY_UPDATE_TEST_ORIGIN`。
- **与源码并排的构建产物会遮蔽该源码，而这种遮蔽是静默的。** 早期某次构建遗留的 606 个未跟踪 `.js`、`.d.ts`、`.map` 文件位于 `packages/*/*/src/` 内。`tsconfig.base.json` 把工作区包名映射到源码**目录**（`./packages/client/ui-slots/src`），而 Vite 的默认解析先试 `.js` 再试 `.ts`，于是每个别名导入都加载了同名模块的过时编译产物，而磁盘上的源码本身毫无问题。上游不跟踪任何此类文件——其 `src/**/*.js` 命中项只有手写的 `css-modules.d.ts` 与 `vite-env.d.ts`——因此修复的全部内容就是按 `git status --porcelain -uall` 报为未跟踪构建产物的那些路径删除残留。`pnpm run clean` 不负责这些文件，而在当前树上执行 `pnpm run build` 也不会重新生成它们。
- **版本对齐须先于发布工具执行，因为该工具会拒绝版本分裂的家族。** `scripts/release/bump.ts` 在规划任何内容之前先校验家族成员共享同一版本，而本次合并让 38 个 fork 包停留在 `0.1.6-alpha.1`、上游则为 `0.1.6-alpha.2`，于是该工具根本无法运行。因此对齐内容是这 38 份 manifest、唯一一处版本镜像（`SIDEBAR_SERVICE_VERSION`）以及 `pnpm install --lockfile-only`。
- **被退休的包目录会作为构建残留存活下来。** `tool-present` 从 `fs` 分组迁往 `deliverables` 时在旧路径下留下了 `lib/` 与 `node_modules/`，而 `check-workspace-constraints` 会拒绝任何缺少 `package.json` 的 `packages/<group>/<pkg>` 目录。`pnpm run clean` 清除该残留；除此外整棵包树均为上游内容。
- **上游自己的测试文件不认识的一项 fork 能力，保留其断言。** `ui-conversation` 的注入面在上游的键之外还带有 fork 的 `releaseViewSetter`，而合并采用了上游的「三键」期望、却保留了 fork 的「四键」面。fork 的断言随之回归，使能力与它的覆盖保持一致；另一条路是为一则写在该能力出现之前的测试而删除一项仍在使用的 fork 行为。
- **被 fork 替换的组件保留 fork 的 spec。** `ui-trajectory` 是 fork 对上游单体大表的重构（`TrajectoryRow` 及其同族位于上游并不具备的 12 个 fork 专属模块中），而上游针对同一文件的 spec 断言的是另一种设计——聚合的预览图库对逐附件行，以及原始视图中本不该出现的图片图库。因此 fork 自有 spec 回归，而先前为让 fork 渲染匹配上游断言的两处移植——compact thinking 变体与逐附件列表——随之一并回退。
- **跟随 fork 自有测试文件而来的上游测试保持上游版本，仅迁移 fork 的 fixture。** fork 的客户端包从 `retainedBy` 获得的一切都需要携带该映射的 fixture，因此 `ui-todo-board`、`ui-patent-teams`、`synapse`、`ui-document-studio` 的 fixture 以 `retainedBy: { mainView: 1 }` 标记当前会话，并以 `uiWorkspace` 替身取代已移除的 `sessions.open`；`SessionListFace` 去掉 `current`。
- **把一条规则与另一条规则对比的样式约定，追踪的是顶层规则。** `ui-sidebar` 中被提升的 workbench 入口必须与 `.newSession` 逐条声明一致，而「轨道覆盖规则赢得同序」的断言现在把搜索锚定在行首：上游的 Windows 标题栏规则在表更早处带有相同的 `.collapsed .newSession` 前缀，会命中裸 `indexOf`。
- **两处文档上限因 fork 的内容而提高，而不是让 fork 的文字缩水。** `docs/architecture.md` 记述 fork 的 desktop-host 组合与 `dsh-host-synapse` 行对，`packages/README.md` 记述 fork 的包分组；两者分别超出上限 23 与 14 个词，因此 manifest 上调至 2440 与 1080，而不是删掉 fork 专有事实。
- **fork 的 pnpm 失效提示在上游的新转发器上回归。** 上游的 `apps/cli/src/plugin.ts` 现在委派给 `@deepseek-ai/dsh-plugin-manager/operations`，并按转发参数的形态打印自己的提示，建议改用 `pnpm-workspace.yaml` 中的 `allowBuilds`——而 fork 的 `2026-09-02-pnpm-plugin-failure-hint-config-homes` 记录已实测该建议在 pnpm 10.34 上会误导，其触发条件同样已被那份记录否决。fork 的 `pnpmFailureHints(stderr, dir)` 分类及其测试在上游转发器之上回归，由后者提供提示所读的 stderr 文本。
- **文档门禁的其余失败是本此同步自身留下的残渣。** 两处相对链接指向本次合并删除或移动的路径（被禁用的 Python 发布工作流、被删除的桌面组合 patch），已归档的 `desktop-without-workspace-sidebar` 三元组未密封，`packages/document` 存在陈旧的子系统页豁免，持久化格式引用集合需要一次 `--write`。

## 后果

fork 交付上游 v0.1.6-alpha.2 基线，并保持其桌面、专利、synapse、插件市场、self-evolve、文档工作台、patent-teams 与待办看板等界面完好，客户端测试道也重新变绿。值得带入下次的是残留遮蔽这一陷阱：fork 的工作树可能把早先某次 checkout 的构建产物与源码并排存放，而由于工作区别名指向目录，混合的树会让解析器对同一模块同时拿到两个候选，且除了一条令人费解的断言外没有任何诊断信息。下次同步应先检查这一点，再去归咎于合并，因为删除这些文件很便宜，而错误定性并不便宜。对齐后的 fork 版本让 `scripts/release/bump.ts` 重新可运行，而桌面回移则让 fork 的 unsigned darwin 打包路径保留自己的测试。

## 考虑过的替代方案

- **采纳上游的 `TrajectoryTable` 及其 spec，并让 fork 的 12 个模块退役。** 否决：上游的表是一个 3511 行的单文件，没有任何位置导入 fork 的 `RecordInspector`、`TrajectoryRow`、`trajectory-record-model`、`trajectory-detail-tabs` 或 `trajectory-resize-handle`，因此采纳它是在删除一个 fork 界面，而不是同步它；而 fork 的 inspector 正是其桌面与工作台界面所挂载的对象。
- **保留上游断言并完成移植，而不是恢复 fork 的 spec。** 基于同样的证据否决：要同时满足两者，就必须移除原始视图的逐块图片图库，而 fork 自有 spec 恰恰断言其存在；可见两份 spec 描述的是两种设计，而同一个组件只能容纳其中一种。
- **通过从 `master` 恢复各 spec 文件来撤销六处客户端 fixture。** 否决：这些文件每一个都同时带有本次发布的上游改动，整体恢复会把上游的覆盖连同 fixture 漂移一起丢弃；因此改为逐字段迁移 fixture。
- **为 `packages/util/http-proxy` 与并行负载下超时的 `browser-use-runtime` 用例提高单测超时。** 否决：在本环境中，同样的两个用例在纯净的 `dsh-v0.1.6-alpha.2` worktree 上同样失败或通过，因此信号来自宿主 DNS 延迟与套件并行负载，而非合并；本地改超时会在日后掩盖真正的回归。

## 测试

`pnpm run test` 通过 1948 个文件，另有两个受环境约束的例外已对照纯净上游 worktree 核实；逐文件覆盖率门禁在 CI 中由 `pnpm run test:coverage` 负责。`pnpm run typecheck`（双面）、`pnpm run lint`（5171 个文件 0 警告 0 错误）、`pnpm run duplication`（0 克隆）、`pnpm run hygiene`（16 项门禁）与 `pnpm run doc-sync`（43 项门禁，含全语料 1264 对配对检查）全部通过，`pnpm run verify-translation-pairing` 已重新登记本次同步触及的每一对。
