# Agent Note: 长执行工具结果快速失败并提示后台化

Status: proposed

[English](2026-09-01-tool-run-fail-fast-and-background-hint.md) | 中文

## 问题

在 `dsh-session-463b73d4` 中，智能体把墙钟时间花在那些已自行定局结果的工具调用上。三次前台 `bash` 调用在恰好默认的 60s 超时处停住调度并被 SIGTERM（一次 `curl` 下载和两次渲染命令），两次 `wait: true` 的 `job_output` 调用的 `wait` 全部跑满（138s 和 144s），尽管后台任务早已以 `Traceback` 退出。智能体直到白等约三分钟后，才改用 `run_in_background` 加轮询。

可用的信号其实存在却未被利用：后台任务在 `wait` 超时前很久就已具备终态输出和退出状态，前台命令也超过了 harness 没能帮智能体预先界定边界的默认超时。

## 提案

在工具结果的计时表面做两处改动。

其一，当前台命令可能超出较短的默认超时时，harness 应在请求时就让它可见：携带显式 `timeout_ms`、或 harness 已能看出是长任务的 `bash` 命令，其结果应提示更长的任务应改用 `run_in_background` 配合 `job_output` 轮询，而不是让一个 step 被阻塞。现有的 `run_in_background`/`job_output` 流程是文档化的出口；结果应明说这一点，而不是等智能体在超时后才重新发现。

其二，`wait: true` 的 `job_output` 应在后台进程已退出——终态退出码或已完成的结果——时就返回，而不是等满超时。返回的载荷携带捕获到的输出和错误，使调用方立刻看到 traceback，而不是在截止时才看到。

## 考虑过的替代方案

- **继续等满截止时间。** 简单，但已死进程仍付出整个 `wait`，正是本会话所示的情况。
- **只加提示、不加提前返回。** 改善下一次尝试，但一个已死的 `job_output` 等待仍会被搁置。
- **只加提前返回、不加提示。** 修好了 `job_output`，但前台超时仍无声无息地 SIGTERM，没有任何引导。
- **自动中止长前台命令。** 过于激进；有些工作本当超过默认值，会被误杀。

## 接受标准

- 达到超时的 `bash` 结果会把 `run_in_background` 加 `job_output` 描述为更长工作的路径。
- 对已退出进程的 `job_output` 等待，会在超时前带着捕获到的退出状态和输出返回。
- 对仍在运行的进程的 `job_output` 等待继续等待（不会提前返回）。
- 无需密钥的测试覆盖已退出、仍在运行两种情形以及前台超时提示。

## 风险

在进程退出时返回必须区分干净退出与仍在产出输出的进程；流式长任务不应因短暂空闲就被过早截断。提示文本也不得变成对「仅超过一次默认值」的受限期前台工作的一条硬性规定。
