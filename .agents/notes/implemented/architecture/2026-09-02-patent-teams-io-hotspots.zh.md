# Agent Note：PatentTeams IO 热点 —— 观察者索引、信箱追加写、spawn 移出团队锁

Status: implemented

[English](2026-09-02-patent-teams-io-hotspots.md) | 中文

## 问题

三个 IO 热点随错误的变量增长。`agent/status` 观察者对进程内每个代理的每次状态变化都全量扫描状态目录（readdir 加每个团队一次 team.json 读取），船长与无关子代理也不例外。`appendMailbox` 每条消息都读取并重写整个 JSONL 信箱，总写入量随消息数平方增长。`addMember` 在团队锁内完成 LLM 路由解析与 `startContinuable` spawn，一次子代理 spawn 期间团队的其他所有工具都被阻塞。

## 决策

- 调度器维护进程内成员索引（`agent id → 团队 + 成员名`，已证实为船长或不在任何团队的代理记为 `null`）。只有 `addMember` 能把存活代理变成成员，因此它在持久化后立即登记新成员；`removeMember` 与 `delete` 负责移除登记。首次目击仍走扫描；此后成员的状态事件只花一次 team.json 读取，船长与陌生代理的事件零开销。负向条目仅在无条目时写入，读到持久化前状态的扫描不会覆盖 spawn 路径刚登记的条目。
- `appendMailbox` 用单次 `O_APPEND` 写入追加一行。一字节尾部探针在文件缺少结尾换行时前置 `\n`，追加记录不会粘到截断的尾行上；文件缺失则新建，其他打开失败（如信箱路径上是目录）照常抛出。
- `addMember` 在锁内做准入校验，在锁外解析路由并 spawn，再在第二个锁窗口内复验并持久化。并发竞争失败的 spawn（团队已结束、重名、超编、写入失败）会先将其孤儿子代理退役（`retired-members.json` 加 interrupt），再向外抛出失败。

## 备选方案

**按子代理 label 前缀过滤状态事件。** 否决：label 归提供者所有（今天是 `subagent-spawn`，`memberProvider` 可配置），任何不在 Agent 上暴露 label 的提供者都会让观察者静默停止调度成员。

**按状态根缓存扫描结果并在写入时失效。** 否决：每次 `writeTeam` 都得知道哪些索引项变了；成员索引只在拥有它的四个服务调用点上变化。

**信箱追加保持 temp + rename 原子写。** 否决：rename 原子性相对单次 `O_APPEND` 写没有增益（被替换的路径同样从不 fsync），却保留了本变更要移除的整文件重写；读取路径本就会跳过损坏行。

**spawn 保留在团队锁内。** 否决：持久子代理 spawn 是 `addMember` 的慢环节，船长添加一个成员会让所有成员的认领/更新/消息调用等它；复验加孤儿退役的窗口覆盖了锁原来排除的竞争。

## 后果

- 并发同名 `add_member` 双方都会 spawn；失败方的子代理被退役，调用方收到明确的准入错误。工具自身的变更本已串行，只有带外竞争才付出一次浪费的 spawn。
- spawn 与持久化之间触发的状态事件会把子代理缓存为非成员；`addMember` 的登记会覆盖它，至多少数早期事件跳过一次状态镜像，下个边界即恢复。
- 代理被缓存后，带外的花名册改动（直接写 `team.json`）对状态观察者不可见，直到进程重启；单进程所有权模型本就排除了这种写入方。
- spawn 期间创建任务时，成员欢迎文本里的任务数可能滞后——仅影响观感；persona 读取的是不可变的团队标识。

## 测试

包内 `vitest run` 全绿（291 个测试）：新用例锁定锁外 spawn（在门控的 `startContinuable` 内部执行一次 `createTask`）、spawn 中途团队结束时的孤儿退役、子代理在自身 spawn 期间上报状态后的状态镜像，以及观察者对已缓存非成员不再扫描。
