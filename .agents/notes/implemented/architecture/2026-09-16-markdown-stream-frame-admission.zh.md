# Agent Note: 流式 Markdown 的每帧经实测预算准入

Status: implemented

[English](2026-09-16-markdown-stream-frame-admission.md) | 中文

## Problem

`MarkdownText` 的流式路径冻结除末尾两个顶层块之外的所有块，只重新解析源文本尾部，因此每帧工作量跟随尾部。而如果整条回复就是**一个不断增长的顶层块**——单个段落、持续追加条目的列表、表格——就没有任何块可以冻结，于是每一帧都要重新解析全文并重建其元素：每帧工作量随回复增长，总工作量随其平方增长。

在 macOS arm64、Node 22.22 上用源码解析探针实测；把 50 KB 按每片 16 字符投递，统计交给文法的源文本量：

| 语料 | 交给文法的源文本 | 相对回复 | CPU |
|---|---:|---:|---:|
| 单个段落 | 78,150,000 | 1563× | 12,440 ms |
| 单个列表 | 75,965,129 | 1542× | 52,757 ms |
| 对照：多个段落 | 617,866 | 16× | 235 ms |

文法自身的成本与块长度成线性——段落 0.17 ms/KB、列表 0.7 ms/KB（128 KB 分别为 29 ms 与 114 ms）——因此在每动画帧一片的到达节奏下，流式渲染占主线程的比例是 `块千字节数 × 0.7 ms/KB ÷ 16.7 ms`。该比例在约 46 KB 的列表或约 193 KB 的段落处越过 100%：从那时起浏览器完全跟不上到达速度，可见回复越落越远，而用户输入要排在解析之后。

解析器无法在不改变用户所见的前提下消除这一成本。在增长中的段落内部切一刀可能切断强调、链接或行内代码；在增长中的列表内部切一刀可能切断一个条目或一段惰性续行，因此后缀重新解析并不等价于一次性解析；出于同样原因，`UNSTABLE_TAIL_BLOCKS` 也不能降到 1。

## Decision

**流式帧要经过实测准入闸门，消息组件负责重试被扣留的帧。**

- 策略归属 `packages/client/ui-primitives/src/markdown/stream-frame-gate.ts`。每帧在运行前先认领、在完成时被计时；超过 `STREAM_FRAME_BUDGET_MS`（4 ms，即 60 Hz 帧的四分之一）的帧，会让其后的帧只在 `实测成本 × STREAM_FRAME_DELAY_FACTOR`（3）之后才到期。
- 源文本短于 `STREAM_FRAME_MIN_SOURCE_CHARS`（4096）的帧无论成本多少一律准入。这里最慢的文法实测为 0.7 ms/KB，因此如此短的回复不可能靠重新解析越过预算；把它扣留下来只会让一次性的调度停顿拖慢一条短回复。
- 被扣留的帧返回上一帧的元素数组，因此 React 不做任何提交，缓存的尾部元素原样复用。
- 被扣留的文本不会丢失：`MarkdownText` 在任何未渲染的帧之后安排 `setTimeout(retryFrame, delayMs)`，重试会渲染当前 prop。因此被扣留的帧会自行落地，无需等待下一个分片。
- 只有追加型帧会被扣留。不再以上次已渲染文本开头的文本属于重写而非本帧的续写，而 `streaming={false}` 按契约走定稿全量解析。
- 唯一调用方是 `StreamingRenderer`（已移到 `src/markdown/streaming-renderer.ts`，与解析器相邻，闸门作为注入依赖），`MarkdownText` 保持为 React 表面。

这套算术就是保证本身。当帧超预算时，无论开放块长到多大，流式渲染占用 `成本 / (成本 + 3 × 成本)`——即帧时钟的四分之一；可见文本最多落后到达内容一个帧成本的四倍；总工作量同时下降，因为被准入的一帧覆盖了更多到达内容（63 KB 列表：1000 次解析 → 334 次，交给文法的量从回复的 500× 降到 102×）。

## Alternatives considered

- **冻结增长块的一部分。** 不采纳：如上所述这类切分并不等价于 DOM 层面的一次性解析，因此它改变的是用户所见，而不只是时机。
- **只渲染有界前缀，其余以纯文本追加。** 不采纳：这会向用户展示并非回复 Markdown 的文本。
- **按追加字节数而非实测成本节流。** 不采纳：与字节成比例的滞后是回复的固定比例——50 KB 块的四分之一是 12 KB，在按 token 节奏的流里是 15 秒——而与成本成比例的滞后只有几帧。
- **仅在连续两帧超预算后才扣留。** 不采纳：它恰好在闸门存在的那个区间里把生效推迟一帧，而最小源文本长度已经覆盖了它本想处理的情形。
- **每个超预算帧固定跳若干帧。** 不采纳：每帧一片与每帧多片都是真实到达节奏，帧数无法换算成主线程时间，实测成本可以。
- **由 owner 而不是渲染器来节流。** 不采纳：解析与元素重建都在同一次渲染调用内部，丢弃 prop 的 owner 两者都躲不开。

## Consequences

长篇单块回复不再饿死主线程，而本包的流式测试仍然逐帧断言与全新挂载的 DOM 相等：准入下限让 4096 字符以下的内容继续走原路径，`markdown-incremental.client.spec.tsx` 中的每个语料都在下限之下。

可见代价就是已记录的滞后：流式文本最多落后到达内容一个帧解析成本的四倍（6 ms 的帧对应 24 ms，44 ms 的列表帧对应 175 ms），释放它的那一帧会显示自上次渲染以来累积的文本。其余行为不变：折叠、fence 高亮、脚注编号与定稿切换都在与之前相同的帧内完成。

闸门是每消息状态。重新定稿、label 身份变化、以及文本被重写都会重置或绕过它，重试定时器随其 effect 一起清理。

## Testing

- `pnpm exec vitest run packages/client/ui-primitives` —— 42 个文件 875 项通过，`src/markdown` 的语句、分支、函数、行覆盖率均为 100%。
- `pnpm exec vitest run packages/client apps/web` —— 7326 项通过；唯一失败项（`keeps every bundled license in the packed client artifact`）在父提交上同样失败，因为工作树中没有构建打包产物。
- `stream-frame-gate.client.spec.ts` 在脚本化时钟上驱动策略：预算内的帧不换取等待，恰好等于预算仍属预算内，超预算帧恰好换取 `成本 × 3`，短源文本在冷却已武装的情况下照样准入，被释放的帧不再报告等待。
- `markdown-stream-frames.client.spec.tsx` 用「每次读取推进固定步长」的时钟驱动 `StreamingRenderer`，因此帧成本由脚本决定而非由机器决定：被扣留的帧返回上一帧的元素数组，重试渲染累积文本，被重写的文档不会被扣留，组件重试 tick 在没有新分片的情况下交付被扣留的文本。它还断言被扣留期间定稿渲染仍完整执行。
- `markdown-incremental.client.spec.tsx` 新增 `holds a stream of one unclosable block to a bounded share of the frame clock`：在建模的文法实测成本（0.7 ms/KB）与每 16 ms 一帧的到达下，准入把解析次数压到帧数的一半以下、把占空比压到 30% 以下、把滞后压到 250 ms 以下。没有准入时同一负载会逐帧解析并超过 100% 占空比，这正是该断言所拒绝的。
- `pnpm run test:bench` —— 9 个文件、49 项通过，含下文新增的浏览器用例。
- 负向控制（已执行并还原）：把 `STREAM_FRAME_BUDGET_MS` 提到 1,000,000 会让三个测试文件中 7 个用例失败（闸门自身的预算用例、渲染器的扣留帧用例、两个组件用例、以及有界占空比用例）；从 `StreamingRenderer.render` 中移除闸门认领会让 4 个合并用例中的 3 个失败。

## Browser measurement

[`benchmarks/markdown-stream-reply`](../../../../benchmarks/markdown-stream-reply/markdown-stream-reply.bench.ts) 在无头 Chromium 中经真实 Web 组合流式输出一个 408 KB 段落——1202 个 340 字符分片、2 ms 间隔，即每个 60 Hz 帧到达四次——并报告共享的 `TaskDuration`、超过 50 ms 的任务数，以及完整回复是否到达转录。同一用例、同一机器，移除准入并重建 Client 产物后：

| | TaskDuration | 占流时长比例 | > 50 ms 任务 | 最长任务 | 转录 |
|---|---:|---:|---:|---:|---|
| 无准入 | 2512 ms / 2949 ms | 85% | 13 | 91 ms | 完整（408,042 字符） |
| 有准入 | 1724 ms / 3013 ms | 57% | 5 | 86 ms | 完整（408,042 字符） |

在更平缓的到达节奏下（同一个 80 KB 块、8 ms 间隔），同一用例报告 58% → 52%，因此闸门的价值取决于到达是否快过帧率。该比例仍明显高于闸门自身的「帧时钟四分之一」，因为 `TaskDuration` 计的是整条分片流水线——SSE 处理、会话投影、React 渲染与提交——而准入只约束其中的 Markdown 帧体。

该用例只报告而不强制时间预算：`benchmarks/AGENTS.md` 要求时间预算先经 CI 硬件上的重复测量，而它尚未在 CI 硬件上跑过。它唯一的断言是完整回复到达转录，这正是准入不得破坏的保证。
