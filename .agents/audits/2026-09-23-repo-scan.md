## 2. 本轮最重的结论：同一仓库两种模式，门禁覆盖一正一反

这是 09-21 只审专利域时看不到、补上文档域后才成立的对比。

| 维度 | 专利模式 `packages/patent` | 文档模式 `packages/document` |
|---|---|---|
| **覆盖率测量** | 家族 glob 在 `coverage.exclude`（`vitest.config.ts:230`）→ 实测 1801 条目中 **0 条** | 不在 exclude → 实测 **32 条全部 100%** |
| 重复检测 | 现行阈值 0 克隆 → 降阈值 **117 克隆 / 888 行** | 现行阈值 0 克隆 → 降阈值 **5 克隆 / 63 行** |
| 性能基准 | 无 | 无（全仓 `benchmarks/` 都无 CI 车道，见 §4） |
| 子进程/网络预算 | 渲染超时硬编码，`Config` 无超时字段 | `office-to-pdf` 22 个预算字段全部进 `Config` |
| 结构债务 | 最大源文件 1684 行；10 个 >150 行函数 | 最大 431 行；本域未见上帝文件 |

证据（HEAD 实跑）：

```sh
$ npx vitest run --coverage --coverage.reporter=json-summary packages/patent
# coverage-summary.json：总条目 1801，来自 packages/patent/*/src 者 0

$ npx vitest run --coverage --coverage.reporter=json-summary packages/document
# packages/document/*/src 条目 32，全部 100%（26 文件 / 443 用例通过）
```

**读法**：文档模式不是「没问题」，而是它的问题（解压炸弹、CRC 性能、契约瑕疵）**在门禁视野内**，所以能被发现和拦住；专利模式的问题（数值范围分叉、invariant 缺 2/9、静默丢弃）**在门禁视野外**，只能靠人工审阅。

最锋利的一处对照：`office-to-pdf` 为 OOXML 配了 `maxArchiveEntries: 10_000` 与 `maxUncompressedBytes: 250 MiB`，而 `docx-kit` 的 `inflateRawSync(payload)` 没有任何输出上限（#227）。

### 需修正的框定（两项）

- **「单侧 `jscpd:ignore` 标记」**：专利域 3 段标记中 3 处为单侧，但放宽到全仓可见，单侧标记是**通行约定**（`tool-pwsh`、`schedule`、`todo`、`commands` 等大量站点都在副本一侧加标记并在文本里写明对端）。机制（一侧掩码 → 整对不报）成立，但「约定即缺陷」的框定需维护者裁定；真正无疑问的是 `paper-download.ts:81`/`:106` 是**裸标记**（无理由文本），而 `AGENTS.md` 要求标记写明理由。已按此修正写入 #209 与 #216。
- **阈值量化**：`jscpd` 的 `minLines` 实际要求打印行数 ≥ `minLines + 1`，故在现行组合（60 tokens / 6 lines）下域内最大**可被报出**的克隆是 **58 tokens**（< 60），「阈值高于域内所有真实克隆」在 HEAD 仍成立。另有 2 条 67/68 tokens 的克隆是 6 行，被行数门拦掉；`minTokens 60` 时 jscpd 只分析 288 个文件，30 时分析 295 个。

## 4. 本轮新发现（不在 09-21 清单内）

### 性能卡点

- **#222（高）fork CI 完全没有性能门禁**：`ci-fork.yml` 无 benchmark job，唯一定义该车道的 `ci.yml` 在 `.github/workflows-disabled/`，而 `scripts/ci-workflow.spec.ts:1200-1214` 的 `loadWorkflow()` 显式回落到归档目录 —— 针对 benchmark 车道的 6 条断言**断言的是一个永不执行的文件**。`docs/testing.md:13` 与 `.zh.md:13` 仍称它是「required Linux PR gate」；`race-stress.yml` 反而有 nightly `cron` 通道，说明「fork 不跑上游 CI」不能解释性能门的缺失。同一扫描还发现 `vitest.web.perf.config.ts` 与 `vitest.web-stress.config.ts` 两条手工通道在所有工作流中 0 命中，`*.perf.ts` 连 typecheck/lint 语料都不在。
- **#224 指令读取无聚合预算**：`agent-instructions/src/files.ts:340` 的 TODO 自述「the render budget is applied only after every accepted file has been read under this per-file cap」，`:423-433` 串行累积全部内容，`:447` 才应用聚合门，`:455` 把已读内容原样作为 `observed` 返回。峰值内存对文件数无界。
- **#227 docx-kit 解压炸弹**：`zip.ts:322` 的 `inflateRawSync(payload)` 无 `maxOutputLength`，docx-kit 内 `maxUncompressed|maxEntries` 零命中；可达链为 `document_deliver`（4 MiB 上限）→ `extractDocxText` → `readZip`。同批还有逐位 CRC-32（约 36.6 ms/MiB）。
- **#226 terminal-bash 三条 PTY 并发 TODO**：`index.ts:112-114`、`session.ts:249-252`、`session.ts:500-504`，共同指向「8 个 per-send 字段应收进一个发送生命周期 owner」；台账 H 段与 09-16 盘点均未载。
