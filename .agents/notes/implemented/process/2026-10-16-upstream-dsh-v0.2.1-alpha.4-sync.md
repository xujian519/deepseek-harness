# Agent Note: upstream dsh-v0.2.1-alpha.4 sync

Status: implemented

English | [中文](2026-10-16-upstream-dsh-v0.2.1-alpha.4-sync.zh.md)

## Problem

The fork moved from upstream's `dsh-v0.2.1-alpha.3` tag to `dsh-v0.2.1-alpha.4`: 89 commits, 831 files, +22,232/−2,044 lines, roughly a quarter of the previous release. The merge base sat on the alpha.3 release merge, which the previous sync landed as a merge commit, so one `git merge` reached the tag and no upstream commit was re-derived. `git merge-tree` predicted 38 conflicting files; the merge produced exactly 38 — eight add/add collisions inside one package directory and thirty content conflicts.

The release collides with the fork on every axis of one subsystem. Upstream added `packages/boot/plugin-market`, `packages/client/ui-plugin-market`, and `packages/experimental/plugin-market-bundle`; the fork already carried `packages/host/plugin-market`, `packages/api/plugin-market-controller`, `packages/extensions/tool-plugin-market`, and its own read-only Settings tab under the same client package path. The two implementations therefore share a filesystem path, a package name, a Cordis service name, and a Remote namespace. Upstream deleted two files.

## Decision

- **The sync branch merge-forwards the release tag.** `sync/upstream-dsh-v0.2.1-alpha.4` carries the merge, and the PR lands it as a merge commit whose first parent is the fork's `master`. A squash would remove upstream's commits from the fork's graph and push the next sync's merge base back to the previous tag.
- **Conflicts are resolved by class, never by line range.** Side-taking by line range preserved lines that held for only one side in the alpha.2 sync.

  | Class | Count | Resolution |
  |---|---|---|
  | `.i18n.yaml` sidecars | 9 | Take the release's, then re-record with `verify-translation-pairing --write` |
  | Generated pages and catalogs | 8 | Take the release's, then re-run every generator |
  | `package.json` manifests | 3 | The fork's side (the release's lists were byte-identical apart from ordering and the release-only packages) |
  | The colliding client package | 8 | The release keeps the path; the fork's content moves to `packages/client/ui-plugin-catalog` |
  | Source and hand-merged prose | 6 | Per file: the fork's version with the release's change edited in |
  | Generators, tests, lockfile | 5 | Union, then re-run the generator |

- **The fork's read-only tab moves to `packages/client/ui-plugin-catalog`.** Upstream's `ui-plugin-market` is an install-capable Discover tab (`DiscoverController`, `market-store.ts`, `remote.pluginManager.installBundle`); the fork's is a read-only discovery tab with no install path. Renaming the fork's package is a one-time cost that makes the path conflict-free at every later release, whereas renaming upstream's would conflict forever. The rename covers the package name, the directory, `PluginMarketTab*` → `PluginCatalogTab*`, the locale namespace `settings.pluginMarket` → `settings.pluginCatalog`, the slot id `market` → `catalog`, the visible label, and eleven reference sites (`tsconfig.base.json`, `tsconfig.client.json`, the web-app bundle's manifest and patch row, two gate scripts, the group README, the ui-theme CSS-radius expectation, the fork's Agent Note, and the generated pages, which the generators rewrote).
- **The service and Remote namespace are renamed, not shared.** The plan recorded this collision as a runtime mutual exclusion hidden behind a default-off experimental bundle. That reading did not survive the first `pnpm run typecheck`: both packages `declare module '@deepseek-ai/cordis'` merging `pluginMarket: PluginMarket` into `Context`, and the two `PluginMarket` classes are different types, so twelve errors landed in `packages/boot/plugin-market/tests`. The Remote layer collides the same way — both the fork's controller and upstream's `dsh-plugin-market/remote` inject a `pluginMarket` member into `TypertRemoteNamespaceMap`, and both the fork's tab and upstream's Discover tab call `ctx.remote.pluginMarket`. The fork's Host service, its Remote namespace, and every reference to them move to `pluginCatalog`; upstream keeps `pluginMarket`, and the two implementations now run side by side without touching. `pluginMarketController` keeps its name — it is the fork's own Remote-controller service and collides with nothing.
- **The release's workflow hardening lands on the fork's active workflows.** Upstream localized every `workflow_dispatch` input description to Chinese and tightened the macOS and Windows packaging source check: the selected preset must be `test` or `production`, a `production` run accepts only `master` or a `dsh-v*` tag, a tag run must have checked out that tag, and a branch run must name a real branch rather than a SHA or PR ref. `DSH_PACKAGING_PRESET` is already bound to `inputs.preset` in both files. The fork's own packaging parameters live in `apps/desktop`, not in these workflows, so nothing the fork relies on was overwritten, and no fork-side content needed restoring.
- **The `webworker-packer` option contraction is absorbed, not restored.** Upstream rewrote `PackOptions` and dropped the `config` string the fork's tests passed to `packVfsImage`; the merge kept upstream's `src` beside the fork's `tests`, so the tree compiled everywhere except the two fork cases in `image-loadable.spec.ts`. Those cases assert only that the vendored `@deepseek-ai/nuo-patent` and the fork's `dsh-patent-knowledge` close over into the image (`result.missing`, `result.files`), which upstream's `roster: [<package>]` expresses directly; the `config` write was never asserted. Weakening the merge back to the old interface would re-derive the conflict at every release.
- **The three "clean but breaks the tree" checks ran before the merge was trusted.** (1) `verify-no-top-level-await`'s spec pins the real tree's excluded list; the fork's `packages/patent/patent-knowledge/src/bin.ts` is a third shebang entry and was added in path order. (2) The release deletes `claim-decor.ts` from `ui-conversation`; both the file and every `ClaimDecoration` reference are gone, and the release's `command-chip-node.tsx`, `command-chip-selection.ts`, and `CommandChip.tsx` are present. (3) `run-gates.ts` gained the release's `no-top-level-await` row inside `sharedHygieneGates()`; the hygiene gate-id spec now names it.
- **The gates the rename disturbed are repaired rather than waived.** `gen-cordis-catalog` maps every rendered service to a documentation page and rejects both a renderable service with no mapping and a stale walk exemption; the fork's `pluginCatalog` keeps the exemption its `pluginMarket` predecessor carried, because the seam's contract lives in `packages/host/plugin-market/README.md` rather than in a subsystems page. `@deepseek-ai/dsh-value` gains `isAbortError` and `toError` in `SAFE_HOST_DEPENDENCY_EXPORTS` — the release's `packages/experimental/inspector` imports both, and both are pure. `apps/cli` declares `@deepseek-ai/dsh-experimental-plugin-market-bundle`, which `app-boot`'s `OPTIONAL_BUNDLES` requires of the launcher. `packages/experimental/client-ui-agent-team` declares `@deepseek-ai/dsh-util-values` in `devDependencies`, the fork's own long-standing omission that this run's dependency gate surfaced. The `no-unknown-casts` baseline swaps the one drifted fingerprint on `tool-plugin-market/src/index.ts` for its replacement, leaving the 1,802-assertion total unchanged.
- **Mechanical alignment.** The root manifest, 47 fork-only manifests (including the new catalog package), and `SIDEBAR_SERVICE_VERSION` move to `0.2.1-alpha.4`. Nine `snapshots/acp/*/stdout.expected.jsonl` files re-pin `agentInfo.version`, the only drift the ACP replay reported. Seventeen translation pairs are re-recorded. Every generator is re-run, and `docs/TECH_DEBT.md`'s counters move to the tree's own measurements (186 long functions, 75 large files, 1,167 `v8 ignore` lines).

## Consequences

The fork ships upstream's v0.2.1-alpha.4 baseline with its patent, self-evolve, desktop, better-sidebar, and document surfaces intact, plus both plugin-catalog implementations living side by side under distinct names.

The lesson this release adds is that a name collision between a fork's subsystem and upstream's is not a runtime property to be recorded and deferred. The plan predicted mutual exclusion at load time inside a default-off bundle, which was true as far as it went; what made it actionable was running the compiler, where the same name collides in the merged `Context` and `TypertRemoteNamespaceMap` interfaces and cannot be deferred. Deferring the rename would have cost every later release the same twelve errors plus a second, larger rename touching the Remote wire.

The `webworker-packer` case is the previous sync's PTC lesson in a new shape: the merge kept upstream's rewritten `src` and the fork's `tests`, so the capability gap showed up as two type errors rather than as a silent feature loss. Type checking one package's tests is what made it visible; nothing in the merge's exit status distinguishes this from a clean merge.

Three divergences still need attention at each release, unchanged: the fork's presets are the merge's landing place for upstream's composition changes, the archived-note seals must match upstream's for the notes it retires, and the fork's notes must track upstream's workflow paths into `workflows-disabled/`.

## Alternatives considered

- **Keeping upstream's `pluginMarket` name and giving the fork's service to upstream's implementation.** Rejected: the fork's tab, tools, and Remote controller project a different wire (catalog sources, `CatalogPage`, install preview) from upstream's index format (`MarketQuery`, `MarketListingEntry`), and the fork's provider serves a bundled offline catalog that upstream's does not. Adopting upstream's would replace a shipped fork capability rather than sync a release.
- **Naming the fork's service only in the Host layer and leaving the Remote namespace as `pluginMarket`.** Rejected: the Remote-layer collision is real — both packages inject the same `TypertRemoteNamespaceMap` member — so the smaller first step would have been followed by the same rename at the wire.
- **Deleting upstream's `plugin-market` packages to keep the fork's names.** Rejected: it discards an upstream feature the fork has no replacement for, and the next sync would reintroduce every file and every conflict.
- **Restoring `PackOptions.config` beside upstream's `roster`.** Rejected: two ways to declare an image's package set drift apart, and the fork's own tests never asserted the config write.

## Testing

`pnpm run typecheck` passes all five gates — Host Typert, host and client compilers, and both aggregates — which is the check that first exposed the service collision.

`pnpm run lint` exits 0 with the one pre-existing unused-disable warning in `packages/experimental/client-ui-cot-translation/src/index.ts`. `pnpm run hygiene` reports 22 of 22 gates passing, including the release's `no-top-level-await`. `pnpm run doc-sync` reports 50 of 51, and `pnpm run verify-module-graph` is current. The one doc-sync failure is `verify-repository-references`, unchanged from the previous sync: `python/sdk/uv.lock` and two lines of the alpha.3 sync note record the decimal string `6344383`, which is the prefix of an object this full-history clone can resolve; the gate's own contract states that an object absent from a shallow history cannot match, so CI's shallow clone cannot report those lines.

`pnpm run test:snapshot` replays 223 keyless cases across the session, sdk, acp, and web lanes with 2 skipped and no failures.

Unit tests for every package this sync touches pass: `host/plugin-market`, `api/plugin-market-controller`, `extensions/tool-plugin-market`, `client/ui-plugin-catalog`, `experimental/webworker-packer`, `api/remotes`, `client/modules`, `core/tools`, `client/ui-theme`, and `subprocess/subprocess-local` — 17 files and 177 cases in the first group, 50 files and 1,134 in the second. The single failure in `subprocess/subprocess-local/tests/spawn-runner.spec.ts` is the known host artifact of this shell exporting `NoDefaultCurrentDirectoryInExePath`; the same file passes 35 of 35 under `env -u NoDefaultCurrentDirectoryInExePath`.
