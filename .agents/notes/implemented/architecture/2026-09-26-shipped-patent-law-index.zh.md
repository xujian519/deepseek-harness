# Agent Note: 随包的专利法条索引与引用判定

Status: implemented

[English](2026-09-26-shipped-patent-law-index.md) | 中文

## Problem

"有哪些条、每条管什么"这件事分散在四处互不相通的地方。`packages/patent/patent-workflow/src/quality-gate.ts` 里有一张主题表，覆盖《专利法》约二十条与《专利法实施细则》一条。`packages/patent/patent-rule/assets/rules/patent/compliance.yaml` 与 `assets/rules/base/citation.yaml` 各自写着同一个"82 条"上限。145 个规则资产把条号写成自由文本的 `legalBasis`。而事实核验技能要求模型把引用对照 `~/.agents/skills/patent-legal/_shared/patent-law-baseline-2024.md`——一个已不再随包交付的 Sati 用户级文件，于是在别的机器上这次对照没有任何可比对象，技能却依然显示为已满足。

门禁上的后果是：落在表外的引用一律判 `unknown` 并放行。每一处《专利法实施细则》引用——包括期限标签自己印出来的条号——都落在这一档，于是流水线可以宣布一份"已核验"的引用清单，而实际上没有任何东西核验过它。

## Decision

`@deepseek-ai/dsh-patent-law` 独占专利域的法条索引与判定词汇，并作为普通函数插件挂在 `patent` agent preset 内。

- **是索引，不是法条文本。** `assets/law/` 每部文书一个文件（《专利法》《专利法实施细则》《专利审查指南》）。条目记录条号或归一化后的指南节路径、主题词，以及文本的来处：`text` / `sourceDoc` / `verifiedOn`。条数上限自带 `maxVerifiedOn`，因为没人核验过的上限不得产出"超出有效范围"的判定。
- **五种判定，而「未核验」不等于「已核验」。** 已核验 / 与所引命题不符 / 条号超出有效范围 / 索引中不存在 / 条文未转录（未核验）。已索引但条文未转录的条目报 `unverified`；超出未核验上限的条号同样报 `unverified`。四种处置各对应一个字段（`onMismatch`、`onOutOfRange`、`onNotIndexed`、`onUnverified`），可选拦截、告警或放行；随包默认对"与命题相矛盾"与"已核验上限之外"拦截，对索引缺口只告警。
- **`law_verify` 是模型可见的那一半。** 它可从文本中抽取引用，也可直接接收引用，逐条对照索引判定，并渲染判定表以及缺口或拦截所意味着的说明。工具描述写明未转录的条文永不报成已核验。
- **两部法律（法规）已转录，指南章节未转录。** 每个《专利法》《专利法实施细则》条目带着它所索引条文的文本、抄录该文本的文书与版本、以及抄录日期，因此法律引用现在会判成 `valid` 或 `mismatch`，不再是 `unverified`。两部法律的条数上限也按同一份文本核验过，这正是让 `out-of-range` 可达的原因。抄录是机械的——从部署的法律语料逐字转录——文件头写明没有人回读复核；`verifiedOn` 记录的是该条目对照 `sourceDoc` 被核对的日期，不是由谁核对的。《专利审查指南》章节只有主题词，因此每条指南引用仍是 `unverified`。
- **人设与两道闸门先读它。** `presets/patent.patch.yml` 的纪律 3、工具与技能段、交付纪律现在都在 cnlaw 之前先跑 `law_verify`；`patent-fact-check` 增加了两步规则（先定形式与索引收录，再查官方原文），`patent-quality-gate` 第 2、7 项跟随它。那条不随包的用户级基线路径已删除。

## Verdict semantics

「索引中不存在」不是"该条不存在"的证据——部分索引无法证明缺失，只有**已核验的**上限可以。覆盖面是刻意部分的：《专利法》索引 82 条中的 36 条、《专利法实施细则》149 条中的 26 条，因此一条存在但未被索引的条文会报 `not-indexed`，理由说明的是本索引没有收录它，而不是该条号有误。「条文未转录（未核验）」两个方向都不传递任何信心：条目的主题词只是索引辅助，命题比对只在条目已有转录文本后才运行。所以处置解析默认让 `notIndexed` 保持告警，而把自己依赖的条目转录完毕的部署，可以在自己的 profile patch 里把 `onUnverified` 收紧为拦截。

现有技术抗辩 / 不视为侵权 / 合法来源三组主题词原本按 2008 年修正的 62 / 69 / 70 条收录。2020 年文本确认了现行修正把同样内容放在 67 / 75 / 77 条，条目随之改到那里，62 条则改按其 2020 年文本承载的强制许可使用费主题收录。改号记录在资产文件头，因为本仓库其他表仍在使用 2008 年编号——在那些表也迁移之前，读者对照时会看到两套编号。

## Why the automatic gates keep their own tables

工作流质量门禁的静态表与 `patent-rule` 的 `citation_analysis` 上限，在本次改动中**没有**改读索引。门禁用自己那套五种判定（`valid` / `unknown` / `unverifiable` / `suspect` / `invalid`）作决定，其中 `unknown` 会放行，而它的表仍在用索引刚刚走出来的 2008 年修正条号——因此接线意味着要决定门禁如何对待索引返回的每一种判定，那是对门禁契约的改动，不是对索引的改动。重复暂时留可见，而不是半修。

## Alternatives considered

**把 Sati 的基线文件随包交付。** 它是一份 13 KB 的 2024 年散文式基线，能零新代码地恢复事实核验路径。它落选，是因为散文无法被索引、比对或逐条检查：门禁读的仍然是人一次性写下的文本，无法区分条文是转录来的还是凭记忆写的，而且文件自带的版本头会与法律本身漂移。

**立刻把索引接进质量门禁与 `rule_check`。** 那样能一步消除重复的上限。它因上面的判定词汇问题落选：在没有已转录条目时，能给出的最强判定就是 `unverified`，把它报成拦截会停掉所有交付，报成放行则重建了索引本要消除的那种虚假信心。

**把条文元数据留在规则资产里、不做成包。** 更省事——上限本来就写在那里。它落选，是因为事实核验技能需要的是一次**判定**，不是一张关键词表，而分散的四处仍然是四处：规则资产能自洽，却回答不了一条引用判定成什么。

**把两部法律整部转录。** 《专利法》82 条、《专利法实施细则》149 条，抄录所用的文本就在手边，因此把 231 个条号全部索引起来可以一次性消掉 `not-indexed` 这一档缺口。它落选，原因在资产的用途：条目是为判定本域实际会写的引用而存在的，169 条无人引用的条文会带着未整理的主题词进来，效果只是把"索引没有它"换成"索引有它但判断不了它"。覆盖面与主题词一样，随引用的需要增长。

## Consequences

默认部署现在按转录后的文本判定法律引用，并让指南引用诚实地停留在未核验；剩下的，是转录部署自己依赖的指南章节，以及决定上文的门禁接线——两者都在这里点名，而非隐瞒。换来的，是这个域有了条号元数据的唯一家、一个能解析模型写出的四种引用形式的解析器，以及一套不可能把未核验条目呈现为已核验的判定词汇；过去回答"这条存在吗"的四处，现在可以收敛到它，而不是彼此漂移。

`patent` preset 没有 recorded-session 快照：它的快照挂载的是一条条独立的行，而不是 preset，因为 preset 属 agent 平面，只有 `dsh-agent-preset-registry` 才能挂载。preset 组成本身由 `packages/bundle/web-app/tests/patent-preset.spec.ts` 钉住；该测试现在还要求：若 `patent-law` 行消失，而人设与技能仍在指示模型调用 `law_verify`，测试必须失败。
